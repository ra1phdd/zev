# Участие в разработке Zev

Спасибо, что помогаете улучшать Zev. Мы приветствуем код, тесты, документацию,
сообщения об ошибках, примеры и обратную связь по продукту.

## Прежде чем начать

1. Проверьте существующие issue и pull request, прежде чем открывать новое обсуждение.
2. Для бага используйте шаблон bug report и приложите минимальное безопасное
   воспроизведение.
3. Для новой фичи опишите пользовательскую проблему, предлагаемое поведение и
   рассмотренные альтернативы.
4. До реализации нетривиальной фичи или изменения провайдеров, TUI, конфигурации,
   хранения, исполнения команд, безопасности или архитектуры сначала откройте issue.
   Это поможет не потратить время на подход, который не вписывается в проект.
5. Небольшие исправления документации и опечаток можно сразу отправлять pull request'ом.

Никогда не добавляйте в issue, тестовые фикстуры, коммиты или pull request API-ключи,
токены, приватную историю команд, персональные данные и другие секреты. Если вы нашли
уязвимость, не публикуйте детали открыто: сначала свяжитесь с мейнтейнером через
приватный канал GitHub.

## Подготовка окружения

Zev — CLI-приложение на Go 1.27.2+. Справочник команд находится в
[`docs/ru/DEVELOPMENT.md`](docs/ru/DEVELOPMENT.md), а факты о репозитории и известные
ограничения — в [`PROJECT.md`](PROJECT.md).

Для полного локального gate нужны:

- Go 1.27.2 или новее;
- `gofmt` (входит в Go), `gofumpt` и `goimports`;
- `golangci-lint` v2 и `deadcode`;
- Git и Bash для скриптов репозитория.

GoReleaser v2 нужен для release-проверок, `entr` — опционально для `make watch`.
Ключи провайдеров и сеть не нужны для unit-тестов.

```bash
git clone https://github.com/ra1phdd/zev.git
cd zev
make build
make run ARGS=version
```

## Ветки и коммиты

- Создайте fork и ветку от `main`.
- Ветка должна быть короткоживущей и содержать одно логическое изменение.
- Используйте понятные имена, например:
  - `feat/add-provider`
  - `fix/history-migration`
  - `docs/improve-installation`
  - `refactor/query-service`
- Делайте коммиты небольшими и удобными для review. По возможности разделяйте
  рефакторинг, изменение поведения и документационные изменения.
- Используйте Conventional Commits с сообщением на английском, например:
  `fix: preserve provider headers across retries`.
- Не коммитьте бинарники, `dist/`, локальную конфигурацию, ключи провайдеров и
  несвязанные изменения форматирования.

## Соглашения проекта

Перед структурным изменением прочитайте
[`docs/ru/ARCHITECTURE.md`](docs/ru/ARCHITECTURE.md). Главные правила:

- `cmd/*` — composition root; бизнес-логика находится в соответствующем пакете
  `internal/entities/*/service`.
- Используйте vertical slices с ports and adapters. Интерфейсы объявляйте на стороне
  потребителя и делайте их небольшими.
- Не добавляйте однострочные обёртки и абстракции «на будущее».
- Функции более чем с тремя содержательными аргументами должны принимать именованную
  структуру параметров. `context.Context` всегда первый и не включается в эту структуру.
- Оборачивайте ошибки через `%w` и явно обрабатывайте возвращаемые ошибки.
- CLI-маршрутизация и представление находятся в `internal/cli`; `cmd/zev` остаётся
  тонким launcher'ом.
- Вызовы локализации используют именованные ключи из
  `internal/core/locale/keys.go`; переводы лежат в английском и русском TOML-каталогах.
- Комментарии в исходном коде пишутся на английском. Документация вне исходников может
  быть на любом из поддерживаемых языков.

## Тесты и локальные проверки

Новое или изменённое поведение должно иметь тесты. Предпочтителен подход test-first,
а для связанных сценариев — table-driven тесты. Провайдеры тестируются через локальные
`httptest`-серверы; unit-тесты не должны обращаться к реальным endpoint провайдеров.

Во время разработки запускайте сфокусированные проверки, а перед PR — полный gate:

```bash
# Применить форматирование Go; после этого проверить diff.
make fmt

# Форматирование, golangci-lint, отчёт deadcode, go vet и unit-тесты.
make check

# Проверка гонок.
make test-race

# Собрать CLI в bin/zev.
make build

# Опциональные black-box-тесты с изолированным HOME и локальными фикстурами.
make test-e2e

# Удалить бинарники локальной сборки.
make clean
```

`make lint` запускает `golangci-lint run --fix`, поэтому может менять Go-файлы.
После него всегда проверяйте `git diff`. Вывод `deadcode` — отчёт для анализа, а не
автоматическое разрешение удалять экспортируемый или платформенный код.

Integration-, e2e- и manual-тесты отделены от стандартного unit-набора. Сквозные
integration-сценарии репозитория находятся в `e2e/` и используют тег `e2e`; старый
target `make test-integration` оставлен совместимым псевдонимом `make test-e2e`.
Manual-тесты требуют явного разрешения и не должны запускаться в CI. Если в репозитории
нет тестов с тегом `manual`, target завершается явной ошибкой вместо ложного зелёного результата:

```bash
make test-integration
make test-e2e
make test-manual ALLOW_MANUAL_TESTS=1
```

Успешная кросс-компиляция не доказывает работоспособность на Windows. Если платформенную
проверку выполнить не удалось, укажите это в PR.

## Изменения документации

Пользовательская документация поддерживается на обоих языках:

- английская: `docs/en/`;
- русская: `docs/ru/`.

Используйте одинаковые имена файлов в верхнем регистре, сохраняйте переключатель языка
в начале файла и обновляйте обе версии в одном pull request. Если изменение влияет на
обнаруживаемость или пользовательское поведение, обновите `README.md`, `README.ru.md`
или `CHANGELOG.md`.

## Как открыть pull request

1. Если ветка устарела, обновите её относительно `main`.
2. Проверьте полный diff, включая новые и сгенерированные файлы.
3. Убедитесь, что PR содержит одно логическое изменение и не содержит секретов.
4. Выполните перечисленные выше проверки и запишите точные команды в описании PR.
5. Откройте PR в `main` и заполните все применимые разделы шаблона.
6. При необходимости свяжите issue через `Fixes #123` или `Refs #123`.

Хорошее описание PR отвечает на вопросы:

- Какую проблему решает изменение?
- Что именно изменилось и почему выбран этот подход?
- Какие тесты и ручные проверки выполнены?
- Меняются ли конфигурация, сохранённые данные, CLI-вывод, поведение провайдера
  или границы безопасности?
- Есть ли вопросы совместимости, миграция, скриншоты или известные ограничения?

Для изменений CLI или TUI, заметных пользователю, добавьте примеры до/после или
скриншоты, если они помогают review. Breaking change нужно явно отметить и описать
переход для пользователей.

## Процесс review

Мейнтейнер может попросить уменьшить scope, добавить тесты или сначала обсудить дизайн,
прежде чем смотреть детали реализации. Отвечайте по существу и обновляйте PR после
учёта замечаний. Зелёные локальные проверки обязательны, но не заменяют review
корректности, безопасности, совместимости и пользовательского опыта.

Не делайте force-push после review, если это усложняет обсуждение; если force-push
необходим, объясните, что изменилось. При слиянии мейнтейнер может объединить коммиты,
чтобы история `main` оставалась читаемой.
