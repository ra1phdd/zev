# Конфигурация

Zev читает конфигурацию из `~/.zev/config` — обычного файла формата `KEY=VALUE`, который
загружается через [godotenv](https://github.com/joho/godotenv) и разбирается
[caarlos0/env](https://github.com/caarlos0/env/v11).

Переменные окружения имеют приоритет над файлом; значения по умолчанию
применяются, если значение не задано ни там, ни там. Файл создаётся и обновляется
командой `zev setup`:

```bash
zev setup              # интерактивный мастер
zev setup mode         # inject | execute
zev setup headers      # произвольные HTTP-заголовки
```

## Значения по умолчанию

Указанные ниже значения применяются в `config.DefaultConfig()`, если соответствующего
ключа нет в `~/.zev/config`.

| Ключ | По умолчанию |
|---|---|
| `LLM_PROVIDER` | `openai` |
| `OPENAI_MODEL` | `gpt-5.6-luna` |
| `OPENAI_BASE_URL` | `https://api.openai.com/v1` |
| `GEMINI_BASE_URL` | `https://generativelanguage.googleapis.com` |
| `GEMINI_MODEL` | `gemini-3.1-flash-lite` |
| `ANTHROPIC_BASE_URL` | `https://api.anthropic.com/v1` |
| `ANTHROPIC_MODEL` | `claude-haiku-5.5` |
| `COMMAND_EXECUTION_MODE` | `inject` |
| `SCRIPT_EDITOR` | `nano` |
| `HISTORY_ENABLED` | `true` |
| `HISTORY_SEMANTIC_ENABLED` | `false` |
| `HISTORY_EMBEDDING_MAX_BYTES` | `32768` |
| `CONTEXT_ENABLED` | `true` |
| `TOOLS_ENABLED` | `true` |
| `TOOL_APPROVAL_MODE` | `manual` |

Домашний каталог пользователя должен разрешаться в абсолютный путь. Отсутствующий
или относительный HOME — ошибка; Zev не переключается на `.zev` текущего проекта.

## Настройки приватности

`HISTORY_ENABLED=false` запрещает этому запросу открывать `~/.zev/history.db`, сохранять
сообщения и запускать JSONL-миграцию. Обычный query не создаёт фоновые embeddings
даже при включённой истории. См. [Историю](HISTORY.md): поэтапное сохранение, отсутствие
ротации, ограничения поиска и приватности.
`CONTEXT_ENABLED=false` запрещает отправку провайдеру сведений об ОС, оболочке,
пользователе, домашнем каталоге и рабочем каталоге. Флаги `--no-history` и
`--no-context` отключают соответствующее поведение для одного запроса. Отключение
истории не удаляет старые записи и не отключает текущий диалог в памяти, передаваемый
провайдеру. Отключение контекста не удаляет сведения, явно включённые в запрос.
Не включайте учётные данные в запросы и команды: их содержимое может попасть
провайдеру, в вывод терминала и во включённую историю.

API-ключи и значения пользовательских заголовков вводятся в маскированном режиме
и скрываются в выводе настройки. Диагностика провайдеров не печатает raw-тела
запросов/ответов, учётные данные и URL endpoint; обычный вывод команд и включённая
история при этом не редактируются. Установщики завершаются с ошибкой, если для
архива нет ровно одной подходящей записи SHA-256 или вычисленный хеш не совпадает.

## Инструменты модели

Инструменты модели включены по умолчанию через `TOOLS_ENABLED=true`.
`TOOL_APPROVAL_MODE` принимает значения `manual`, `auto` или `bypass`; это значение
проверяется даже при отключённых инструментах. Переменные окружения имеют приоритет
над файлом конфигурации, а флаги `--tools`, `--no-tools` и `--tool-approval` имеют
приоритет над обоими источниками.

Инструменты отключаются для запроса при `--no-context` или `CONTEXT_ENABLED=false`,
поэтому рабочий каталог не может утечь через выполнение инструмента. Явный флаг
`--tools` переопределяет это ограничение приватности. В режимах `--print` и `--json`
`--tools` нужно указывать явно; эти режимы никогда не открывают TUI, даже в терминале.
Ручной вызов инструмента в machine mode возвращается модели как отказ с пояснением
явно выбрать `auto` или `bypass`.

Модель получает native-функцию `exec` с полями `command`, `args` и `reason`. Аргументы —
точный массив argv, а не строка для неявного shell. Нужна модель/endpoint с function
calling; если endpoint его отклоняет, используйте `--no-tools`. Обмен поддерживается
адаптерами OpenAI-compatible/Ollama, OpenCode, Anthropic и Gemini.

- `manual`: каждый вызов и фиксированный рабочий каталог показываются в stderr; требуется
  буквальное `yes`. Пустой ввод, отказ, отмена или отсутствие терминала не разрешают
  исполнение. Подтверждение действует только на один конкретный вызов.
- `auto`: сначала применяется локальная read-only политика, затем перед каждым допущенным
  вызовом идёт **отдельный запрос к настроенному provider/model**. Проверяющая модель не
  получает инструменты, основной диалог или содержимое файлов: только argv, причину и
  корневой каталог. Выполнение разрешает только однозначный JSON-вердикт. Опасность,
  ошибка сети или некорректный ответ означают отказ с пояснением основной модели, чтобы
  она могла выбрать другой способ. Один вердикт модели не является границей безопасности.
- `bypass`: произвольные исполняемые файлы с правами пользователя, без подтверждений и
  проверяющей модели; в stderr выводится предупреждение. В manual/bypass можно явно
  вызвать shell, например `sh -c`. Это **не sandbox**: возможны запись файлов, сеть и
  раскрытие секретов. Дочерний процесс получает минимальное окружение вместо ключей и
  заголовков Zev, но может читать доступные ему файлы. Исполняемые файлы ищутся в системных
  каталогах; для остальных задавайте абсолютный путь. stdin закрыт: интерактивные команды
  не поддерживаются.

### Контракт адаптера локальных инструментов

Авторизация вызывающей стороны и изолированная проверка моделью относятся к сервису,
который использует адаптер, а не к адаптеру файлов/процессов. В `auto` сервис выполняет
описанный выше отдельный запрос проверяющей модели; во всех режимах `Execute` заново
проверяет весь запрос. Ни лексическая проверка, ни решение reviewer не являются постоянным
разрешением.

Режим `auto` использует эти встроенные операции, а не исполняемые файлы из `PATH`.
Адаптер ограниченного режима принимает только следующие точные формы argv:

```text
pwd                  # без аргументов
ls                   # только корень, один уровень
ls PATH              # один каталог, один уровень
cat PATH             # один обычный файл с одной жёсткой ссылкой
head PATH            # первые 10 строк, разделённых LF
head -n N PATH       # каноническое десятичное N в диапазоне [1, 1000]
```

В адаптере нет поиска в PATH, запуска subprocess, неявного shell, stdin,
glob, expansion, разбора произвольных опций, рекурсии, режима нескольких путей или
других флагов (включая `--`). Shell-метасимволы в пути — буквальные байты имени, а не
инструкции. `ls` выдаёт имена в ASCII Go-quoted формате, в порядке файловой системы,
без метаданных; symlink, чувствительные имена и неоднозначные для платформы имена
исключаются.

Относительные пути начинаются от настроенного корня; абсолютные разрешены только внутри
него. Любой лексический компонент `..` отклоняется, даже если результат остался бы
внутри корня; каждый относительный компонент проверяется до и после очистки. Отклоняются
имена, начинающиеся с `-`, содержащие двоеточие или неродной обратный слеш, а также
заканчивающиеся точкой или пробелом (кроме `.`). Symlink в любом компоненте, включая
настроенный корень и его предков, запрещён. `New` не канонизирует aliases: composition
root может канонизировать доверенный cwd до создания адаптера, но не должен
канонизировать недоверенный tool path для обхода проверок.

Проверка чувствительных имён регистронезависима и распространяется на предков корня.
Отклоняются `.env*`; любое имя, содержащее `credential`, `secret`, `password`, `token`,
`privatekey`, `private_key`, `private-key` или `keys`; точные `.git`, `.ssh`, `.aws`,
`.kube`, `.azure`, `.gnupg`, `.zev`; `id_*`; суффиксы `.pem`, `.key`, `.p12`, `.pfx`.
Это намеренно блокирует некоторые безобидные имена и не распознаёт секреты под обычными
именами. Файлы должны быть обычными и без нескольких жёстких ссылок.

Корень закреплён до закрытия; каждая операция проверяет, что текущий путь всё ещё
указывает на ту же identity. Каталоги-потомки открываются по одному компоненту через
`os.Root`, а identity после открытия должна совпасть с предварительной метаинформацией
об отсутствии symlink. Дескрипторы файлов проверяются до чтения. На Unix используются
`O_NOFOLLOW|O_NONBLOCK`, чтобы замена файла на FIFO не блокировала open; на Windows
проверяются число жёстких ссылок и reparse attributes уже открытого дескриптора.

Фиксированные лимиты адаптера: 32 КиБ совокупного stdout/stderr (включая экранирование),
32 769 байт чтения одного файла (`head` может читать этот ограниченный префикс даже
если строк меньше), максимум 1024 записи `ls` (включая пропущенные),
4096 байт и 64 компонента для каждого пути и корня, 64 аргумента, 4096 байт на
исполняемый файл/аргумент, 16 384 байта на исполняемый файл вместе с аргументами и
2048 байт на `reason`. `reason` не выполняется. `ls` не сортирует и не обходит рекурсивно;
достижение лимита записей консервативно выставляет `Truncated` даже на точном EOF.
`Truncated` означает достижение лимита, а не согласованный снимок файловой системы.
C0/C1 кроме LF и tab, CR и Unicode format controls экранируются; некорректный UTF-8
заменяется. Вывод дочернего процесса не пишется в stdout/stderr приложения; перед
выводом в терминал вызывающая сторона должна заключить результат в JSON-кавычки.

Каждый `Execute` получает deadline десять секунд, сокращаемый deadline вызывающей
стороны. Native-процессы используют `childprocess.Run`, включая очистку process group/job
и ограниченное чтение pipe; очистка может продлить wall-clock время сверх deadline.
Обычные filesystem API не умеют отменять уже выполняющийся kernel-вызов: адаптер
проверяет отмену вокруг ограниченного I/O, но зависший filesystem/FUSE/kernel-вызов
не получает жёсткого wall-clock лимита. Это нельзя рекламировать как hard timeout.

При `restricted=false` вызывающая сторона уже разрешила полный запрос. `os/exec` получает
буквальный argv и `cwd=root`; shell запускается только при явном запросе. stdin — null
device. Окружение содержит только `PATH`, `LANG=C`, `LC_ALL=C` и, на Windows,
`SystemRoot`; ключи и заголовки провайдера, `HOME`, loader hooks и переменные запуска
shell не наследуются. Простые имена исполняемых файлов ищутся только в `/usr/bin:/bin`
или `SystemRoot/System32` на Windows и только как `.exe`; явные абсолютные пути или
относительные пути с разделителями могут выбирать другие программы.

Ручное и bypass-выполнение не являются sandbox: разрешённые команды могут менять файлы,
выходить в сеть, читать доступные credentials или намеренно отделять потомков.
`os.Root` не запрещает переход через mount, а адаптер не защищает от враждебных процессов
того же UID, изменений mount или одновременного изменения данных обычного файла.
Фильтрация имён не обнаруживает секреты в содержимом; не включайте инструменты в
недоверенном или содержащем секреты проекте, не учитывая, что будет отправлено
провайдеру.

```bash
zev query --tool-approval manual "изучи проект"
zev query --tool-approval auto "найди подходящую команду сборки"
zev query --print --tools --tool-approval auto "найди команду тестирования"
zev continue --tool-approval auto "разберись в ошибке"
zev query --no-tools "покажи использование диска"
# Явное отключение подтверждений и проверки безопасности:
zev query --tools --tool-approval bypass "изучи проект"
```

Постоянные настройки в `~/.zev/config` используют обычный dotenv-формат:

```dotenv
TOOLS_ENABLED=true
TOOL_APPROVAL_MODE=manual
```

Лимиты: **8 вызовов на ответ, 10 секунд на локальный вызов, 30 секунд на проверку,
2 минуты на цикл, 32 КиБ совокупного stdout/stderr одного вызова**, 256 КиБ совокупных
сериализованных результатов. Это deadlines отмены, а не жёсткие wall-clock гарантии:
очистка процессов может занять больше времени, а зависший kernel/filesystem syscall не
прерывается этим in-process адаптером. При лимите вызовов модель завершает ответ без новых
инструментов. Вывод может обрезаться; при отмене управляемые дочерние процессы очищаются.
Инструменты увеличивают расход токенов. Промежуточные данные инструментов и проверки не
сохраняются в историю; итоговый ответ модели может повторить прочитанную информацию.
`--print`/`--json` не выполняют итоговую предложенную команду; явный `--tools` разрешает
только выполнение инструментов сбора контекста. `doctor`, разрешение алиасов и просмотр
скриптов не вызывают инструменты модели. Native runtime на Windows не проверялся;
кросс-компиляция сама по себе не доказывает корректность на целевой ОС.

Настройки независимы от LLM команд; его ключи и заголовки не наследуются автоматически.
Требования к провайдеру проверяются только при включённом semantic search; значения
окружения всё равно должны разбираться в объявленные типы. Клиент добавляет `/embeddings`
к API root и отклоняет credentials в URL, query string и fragment.
Слишком длинный ввод отклоняется, а не обрезается молча.

Допустимы только начальные user-сообщения и уточнения. Удалённый embedding-запрос раскрывает
их текст, а semantic/hybrid также передаёт текст поискового запроса. Локальный прокси может
пересылать его наружу. Включение настройки не индексирует старые сообщения автоматически
и не добавляет найденную историю в LLM prompt. При включении CLI использует настроенный
клиент для semantic/hybrid-поиска и явного rebuild векторов; обычный query не создаёт
векторы. `zev history index rebuild --vectors --yes` показывает провайдера/модель и общее
число допустимых сообщений и требует явного согласия на передачу. `--retry-failed`
повторяет ошибки; `zev history index rebuild --fts` обновляет локальные индексы без
embedding-запросов. Команды, покрытие и лимиты кандидатов описаны в [Истории](HISTORY.md).

### Поведение

| Переменная | Описание |
|---|---|
| `COMMAND_EXECUTION_MODE` | `inject` — попытка вставки команды в терминал; `execute` — немедленное выполнение первого варианта |
| `SCRIPT_EDITOR` | Редактор для `zev script create` |
| `HTTP_HEADERS` | Список пар `Key:Value` через запятую, добавляемых к каждому запросу. Регистр ключей сохраняется |
| Политика повторов | Запросы к провайдерам повторяются до 3 раз при HTTP-ответах `429` и `5xx`. Используется экспоненциальная задержка (`1s`, `2s`, `4s`); корректный `Retry-After` может её увеличить, но задержка не превышает 30 секунд. Повторы логируются на уровне warning, окончательная ошибка — на уровне error. |

Redirect провайдера разрешён только в пределах исходного origin (схема, хост и порт).
Переход на другой origin отклоняется до отправки запроса, включая SDK credentials и
пользовательские `HTTP_HEADERS`. При создании клиента сохраняется копия карты заголовков.

## Повторы запросов к провайдерам

Все пять провайдеров используют общий HTTP-клиент с повторами как для одиночных
запросов, так и для истории диалога. Всего не более четырёх попыток: исходный
запрос и три повтора. Существующий таймаут клиента в 30 секунд включает все
попытки, задержки и чтение ответа, поэтому таймаут или отмена могут остановить
операцию раньше. Остальные `4xx` и некорректный JSON в успешном ответе не
повторяются. Поток после HTTP `200` не запускается заново при обрыве во время
чтения. Предупреждения о повторах видны без `-v`; URL, API-ключи и содержимое
запросов в retry-логи не попадают. Дополнительная настройка не требуется.

## Проверка ответов и лимиты

Все пять провайдеров проверяют подсказки до выбора, выполнения и сохранения в
историю. Существующая история также проверяется перед выбором команды. Фиксированные
лимиты: **3 варианта**, **4096 байт UTF-8 на команду**, **2048 байт UTF-8 на
пояснение**, **32 КиБ структурированного JSON-ответа** и **256 КиБ тела HTTP-ответа
провайдера** (включая SSE-обрамление OpenCode). Это ограничения байтов, а не числа
символов; они не настраиваются. Пустые команды, некорректный UTF-8, превышение
лимитов и несогласованная структура успешного/отклонённого ответа приводят к ошибке.

В тексте ответа запрещены управляющие символы, кроме tab, LF и CR. Вставка в
терминал строже: **все управляющие символы**, включая эти три, отклоняются до записи
любого ввода в терминал. Многострочная подсказка всё ещё может быть показана как
fallback или выполнена в режиме `execute`. Валидация не очищает shell-синтаксис,
не является sandbox и не гарантирует безопасность предложенной команды.


## Файлы проектного контекста

К запросу можно добавить один или несколько ограниченных файлов:

```bash
zev --context-file README.md -cf docs/ARCHITECTURE.md "объясни путь запуска"
zev --print --context-file README.md "найди нужную команду"
zev --json --context-file README.md "найди нужную команду"
```

`--context-file` и `-cf` можно указывать несколько раз. Пути разрешаются относительно
текущей рабочей директории и не могут выходить за её пределы. Принимаются только обычные
файлы; директории, symlink, `.env`, private keys, credential-подобные файлы и компоненты
путей (включая `.aws`, `.docker`, `.ssh` и `.kube`) отклоняются
до сетевого запроса. Размер одного файла ограничен 64 КиБ, общий размер — 256 КиБ.
`--allow-sensitive-context` — отдельное явное разрешение для намеренно выбранного
чувствительного файла; symlink всё равно запрещён. Ошибка контекста не вызывает сеть,
а machine mode сохраняет исходный контракт stdout.


## Язык интерфейса

CLI и интерактивные подсказки поддерживают английский и русский через `go-i18n`.
Явный выбор: `ZEV_LANG=en` или `ZEV_LANG=ru`. Без переопределения используется первое
непустое значение `LC_ALL`, `LC_MESSAGES`, `LANG`, включая `ru_RU.UTF-8`.
Для неподдерживаемого языка используется английский.

```bash
ZEV_LANG=ru zev query "показать файлы"
ZEV_LANG=en zev alias list
```

Переводы находятся в корневом `locale/*.toml` и встраиваются в бинарник: дополнительные
файлы рядом с установленной программой не нужны. При добавлении переводов сохраняйте ID,
printf-параметры и имена команд/флагов. Go-код использует именованные константы из
`locale/keys.go`, а не английские предложения; изменение перевода не меняет ID. JSON-ключи и статусы, предложенные команды, тела
скриптов, ответы провайдера и сохранённая история не переводятся. Низкоуровневые ошибки
системы/библиотек могут оставаться на английском.

## Продолжение после ошибки

```bash
zev continue
zev query --continue
zev query --continue --print "повторить после исправления команды"
```

`zev continue` — синтаксический сахар для `zev query --continue`. Команда восстанавливает
последний пригодный завершённый или ошибочный запрос и сохраняет полный упорядоченный
транскрипт, а не только последний prompt. В интерактивном режиме Zev последовательно
предлагает прикрепить файлы проекта, вставить лог/ошибку команды и ввести уточнение.
Enter пропускает шаг; необходимо указать хотя бы файл, лог или уточнение. В machine mode
TUI не открывается, а stdout-контракт сохраняется.



```bash
zev alias edit <name>
zev script edit <name>
zev script show <name>
```

`alias edit` открывает сохранённый шаблон алиаса и сохраняет его после успешного выхода
редактора, если шаблон не менялся с начала редактирования: устаревшая копия не затирает
новую версию. Список алиасов сортируется по имени. `script edit` открывает зарегистрированный Bash-скрипт через `$SCRIPT_EDITOR`,
`$EDITOR`, `nano`, `vim` или `vi`. `script show` выводит точное тело скрипта в stdout
без выполнения; используется безопасное чтение файла без запуска внешнего shell.

## Машинный вывод

Для скриптов и CI machine mode не открывает selector, не вставляет ввод в терминал,
не запускает shell и не выполняет полученную команду:

```bash
zev --print "find large files"
zev --print --option 2 "find large files"
zev --json "find large files"
```

`--print` пишет в stdout только выбранную команду. `--json` использует схему версии 1:
`{"schema_version":1,"status":"ok","selected_option":1,"commands":[...]}`.
Предупреждения, прогресс и ошибки идут в stderr. Нумерация вариантов начинается с 1,
по умолчанию выбирается 1; отсутствующий вариант оставляет stdout пустым и возвращает ошибку.
Стабильные exit codes machine mode: 0 — успех, 2 — аргументы/выбор варианта, 3 —
провайдер/конфигурация, 4 — некорректный ответ провайдера, 5 — ошибка чтения локального
контекста. `--print` разворачивает алиасы без исполнения. Сохранённые скрипты автоматически
не печатаются; используйте `zev script show <name>` для просмотра тела.


## `zev doctor`

`zev doctor` сначала выполняет только локальные проверки: загрузку конфигурации,
выбранного провайдера, обязательной модели, наличия API-ключа, синтаксиса base URL,
режима выполнения, shell/editor, приватности прав `~/.zev`, чтения истории и разбора
CLI-режимов. Наличие ключа означает только `configured`; рабочесть ключа проверяется
только отдельным подтверждённым сетевым запросом.

```bash
zev doctor             # статика, затем интерактивный вопрос да/нет
zev doctor --print     # только статика, человекочитаемый вывод
zev doctor --json      # только статика, версионированный JSON
zev doctor --confirm   # статика и один реальный запрос к провайдеру
zev doctor --json --confirm
```

JSON использует `schema_version: 1`, поля верхнего уровня `status`, `checks` и
`actionable_message`. Doctor никогда не выводит API-ключи, значения заголовков,
URL провайдера или тела ответов.

## Режим выполнения команд

`zev setup mode` определяет способ обработки подсказок:

- `inject` (по умолчанию) — выберите подсказку, проверьте вставленную команду и
  нажмите Enter. Если вставка не поддерживается или запрещена, Zev печатает команду.
- `execute` — **первый вариант** выполняется сразу, без селектора и подтверждения.
  Предупреждение об опасности выводится после выполнения и не является защитным барьером.

Алиасы и сохранённые скрипты выполняются напрямую независимо от этой настройки.

CLI передаёт отмену Ctrl-C/SIGTERM в запросы провайдера, ожидание повторов,
интерактивный ввод и выполнение дочерних процессов. Дочерние процессы используют
отдельную Unix-группу или Windows kill-on-close job. На Unix оставшиеся управляемые
потомки группы завершаются при отмене или обычном выходе ведущего процесса, до его
reap. На Windows процесс создаётся приостановленным, включается в job и только
затем возобновляется; очистка job завершает оставшиеся управляемые процессы.
Это не изоляция: Unix-процессы,
отделившиеся в другую группу/сессию, и процессы, созданные через внешние брокеры,
находятся вне этой границы. Очистка pipe не ограничивает произвольный блокирующий
I/O, переданный вызывающей стороной. Поведение Windows требует проверки на самой
Windows; одной кросс-компиляции недостаточно.

## Выбор редактора для `zev script create`

1. `$SCRIPT_EDITOR`
2. `$EDITOR`
3. первый доступный из `nano`, `vim`, `vi`

Редактор получает приватную временную рабочую копию, а не путь зарегистрированного
скрипта. После успешного редактирования данные записываются во staging-файл,
синхронизируются и атомарно заменяют оригинал только при совпадении идентичности
исходного файла: устаревший редактор не перезапишет новую версию другого
участвующего в протоколе редактора. Поддерживается сохранение через rename.
Symlink, специальные файлы и скрипты/рабочие файлы с несколькими жёсткими ссылками
отклоняются.

Начальный скрипт регистрируется до открытия редактора. Если редактор не найден,
завершается с ошибкой или отменён, зарегистрированный скрипт остаётся, а временная
рабочая копия очищается. Указанный в ошибке временный путь не является постоянным
файлом для восстановления. `SKIP_EDITOR=1` отключает открытие редактора.

## Файлы на диске

| Путь | Содержимое |
|---|---|
| `~/.zev/config` | Конфигурация, строки `KEY=VALUE` |
| `~/.zev/history.db` | Постоянная SQLite-история диалогов без ротации по количеству |
| `~/.zev/history` | Старый JSONL: автоматически импортируется/архивируется при открытии repository из query или команд истории |
| `~/.zev/history.migrated.*.jsonl` | Сохранённый старый архив, не активное хранилище |
| `~/.zev/aliases` | Шаблоны алиасов, YAML |
| `~/.zev/scripts` | Метаданные скриптов, YAML |
| `~/.zev/script_files` | Тела скриптов |

`~/.zev/scripts` — это файл, а `~/.zev/script_files` — каталог: файл и каталог с
одинаковым именем не могут сосуществовать.

### Безопасность хранилищ и границы восстановления

Конфигурация и алиасы записываются во временный файл в том же каталоге с последующей
заменой; кооперативная блокировка охватывает чтение–изменение–запись. SQLite-история
использует WAL-транзакции вместо перезаписи JSONL.
На Unix файлы записываются с режимом `0600`, новые каталоги приложения — `0700`,
новые тела скриптов — `0700`. Эти права не шифруют API-ключи или историю; режимы
Unix не доказывают аналогичное поведение Windows ACL.

Постоянные sidecar-файлы `*.lock` задают идентичность межпроцессной блокировки:
**не удаляйте и не заменяйте их**, даже когда они не используются. Symlink вместо
файлов данных или `~/.zev` отклоняются; lock-файлы должны быть обычными файлами
с одной жёсткой ссылкой. Алиасы в доверенных родительских каталогах (например,
symlink в пути домашнего каталога) допустимы. Это кооперативный протокол, а не
sandbox против враждебного процесса того же пользователя или записи в обход lock.
Повреждённое хранилище вызывает ошибку, а не тихий сброс. Повреждённый legacy-источник
блокирует активацию миграции вместо потери предыдущих записей. Логическое удаление не
стирает копии из WAL/свободных страниц, экспортов, backup и JSONL-архива. Активную
WAL-базу копируют согласованным SQLite-снимком, а не копированием только `history.db`.

Пути в метаданных скриптов должны быть относительными внутри `script_files`:
абсолютные пути, traversal, symlink в компонентах приложения и несколько жёстких
ссылок у файла скрипта отклоняются. Выполнение читает уже открытый проверенный
скрипт, а не повторно открывает проверенное имя. Создание/удаление сериализует
изменения метаданных и тела и пытается откатить ошибки до фиксации, но **не является
crash-atomic транзакцией сразу над обоими файлами**.

При атомарной замене ошибка до rename оставляет прежний файл неизменным. Ошибка
синхронизации каталога после rename означает, что новая версия уже видна, но её
сохранность после аварии неизвестна; это не доказательство отсутствия изменений.
Go-код распознаёт это через `errors.Is(err, filestore.ErrCommitted)` или
`ErrCommitted` репозитория скриптов. Перед повтором файлового изменения проверьте
текущее состояние. Ошибки очистки также могут сопровождать уже
завершённое изменение. На Windows здесь нет переносимого directory-fsync;
аварийную сохранность и runtime-поведение нельзя выводить из успешной кросс-сборки.
