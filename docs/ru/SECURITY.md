# Реализованная безопасность и ограничения

Здесь описано фактическое поведение текущей реализации Zev. Проверки безопасности являются policy уровня приложения, а не sandbox операционной системы. Схема YAML описана в [Конфигурации](CONFIGURATION.md), полный список флагов — в [справочнике CLI](CLI.md).

## Границы доверия

Zev считает недоверенными ответ провайдера, запросы и результаты tools, файлы проекта, вывод команд, сохранённые алиасы/скрипты и загруженные веб-страницы. Эти данные можно использовать как task data, но они не меняют локальную policy и не создают согласие. Источником авторизации является текущий запрос пользователя и явное подтверждение в prompt; объяснение модели и её флаг `dangerous` не являются разрешением.

Zev не защищает от скомпрометированных ОС/ядра, администратора или враждебного процесса того же пользователя. Lock-файлы координируют только сотрудничающие процессы Zev. Approval, анализ команд, path checks и capability descriptors не изолируют произвольную host-команду от файлов, сети, credentials и других ресурсов хоста.

## Доставка команд

### `inject` (по умолчанию)

Zev выбирает команду и пытается вставить её во ввод терминала. Enter не нажимается. При наличии предупреждения до вставки показываются точная команда и предупреждение. Это **warning-only**: после отправки текста пользовательская оболочка сама выполнит его, а Zev не контролирует и не наблюдает этот запуск. Если вставка не поддерживается или отклонена, команда печатается. При частичной вставке не отправляйте ввод терминала, сначала проверьте его.

При `command_wrapper_enabled: true` (по умолчанию) сгенерированная инъекция оборачивается в `zev run '<команда>'`. Это позволяет после последующего запуска сохранить ограниченный вывод ошибки и предложить recovery. Значение `false` отключает только автоматическую обёртку; явный `zev run '<команда>'` остаётся доступен. Обёртка для инъекции не поддерживается в Windows. Обёртка не превращает injection в sandbox и не авторизует выполнение самим Zev.

### `execute`

`execute` выполняет первый вариант провайдера через выбранную host shell. Локальный анализ использует ограниченный структурный поднабор разрешённых `sh`, Bash или Zsh и не запускает команду во время анализа. Известные опасные операции и неполный/неподдерживаемый анализ требуют подтверждения при `security.mode: auto`; deny-rule отклоняет действие. Для неизвестной команды автоматический запуск сначала отправляет точную команду, исходный запрос пользователя и короткое объяснение в отдельный ограниченный safety-review запрос к настроенному провайдеру. Таймаут, ошибка провайдера, malformed/неоднозначный ответ или небезопасный verdict останавливают выполнение. Remote review не отменяет локальное dangerous finding или deny-rule.

Явное подтверждение действует только для текущей операции. Оно не делает команду безопасной и не становится постоянным разрешением. `security.mode: bypass` пропускает permission prompt для технически валидной host-доставки `execute`; matching deny-rules продолжают применяться к этому пути. `inject` намеренно остаётся warning-only и не использует эти permission decisions, так как выполнение передаётся shell пользователя. `bypass` не является sandbox и не гарантирует безопасность.

### Управляемые алиасы и скрипты

Алиасы и скрипты выполняются напрямую независимо от `command_execution_mode`. Команды алиасов проходят структурный анализ; опасные или неизвестные команды требуют подтверждения в `auto`. Тело сохранённого скрипта считается opaque/unanalysed: пользователь видит предупреждение с SHA-256 точного тела, а в `auto` требуется подтверждение. Deny-rule всё равно отклоняет действие; `bypass` пропускает подтверждение, но не меняет host privilege boundary.

Тело скрипта читается в ограниченный immutable snapshot до авторизации, и выполняется именно этот snapshot. Замена pathname после approval не подменяет байты программы. В Unix скрипт запускается через Bash с унаследованным дескриптором и literal-аргументами. В Windows выполнение скриптов недоступно до появления проверенного handle-safe Bash transport. Выполнение алиасов также недоступно в Windows: в Unix требуется allowlisted POSIX-compatible shell.

## Конфигурация policy

Раздел `security` имеет отдельную версию схемы (`1`). По умолчанию используются `mode: auto`, `default_decision: ask`, локальные probe/classifier и поведение `ask` при ошибке. В версии 1 нет model-based probe/classifier и нет OS sandbox. `security.mode: normal` принимается как legacy-название `auto` и нормализуется при сохранении; legacy-настройки sandbox не поддерживаются.

Правила группируются как `deny`, `ask` и `allow`. У каждого правила уникальный непустой ID и непустой `match`. Поддерживаются selectors для sources, deliveries, effects, paths, executables, argv prefixes, certainty и risk. Поля одного match объединяются конъюнктивно; значения внутри одного списка — альтернативы. Path selectors поддерживают `${workspace}`/`${home}` и component-aware `*`/`**`. Приоритет всегда **deny > ask > allow**, независимо от порядка YAML. Allow должен покрывать все запрошенные effects; частичное покрытие не выдаёт разрешение. Глобальный default может быть только `ask` или `deny`, но не `allow`. Неизвестные и невалидные значения останавливают валидацию конфигурации до dispatch.

Пример:

```yaml
security:
  version: 1
  mode: auto
  default_decision: ask
  rules:
    deny:
      - id: deny-policy-edits
        match:
          effects: [security_policy_change]
    ask:
      - id: confirm-network
        match:
          effects: [network]
```

Используйте только реально поддерживаемые значения selectors из [Конфигурации](CONFIGURATION.md); пример показывает форму, а не добавляет capabilities.

## Model context tools

Для tools действует отдельный `tool_approval_mode` (`manual`, `auto`, `bypass`), независимый от `security.mode`.

- `manual` показывает точный запрос и фиксированный рабочий каталог в stderr; `y` или Enter подтверждают, `n` отклоняет, Esc отменяет. Отсутствие терминала, отмена или отказ означают denial.
- `auto` разрешает только ограниченные встроенные операции `pwd`, `ls`, `cat`, `head` в настроенном root. Перед каждым вызовом выполняются локальная проверка и отдельный tools-disabled review. При исполнении проверки повторяются. Ошибка review/сети или неоднозначный ответ отклоняют вызов.
- `bypass` пропускает prompt/reviewer, но сохраняет те же builtin и проверки. Он не разрешает произвольные процессы, shell, запись или сеть через `exec`.

`--print`/`--json` не включают tools неявно; для opt-in нужен `--tools`. `--no-context` или отключённый `context_enabled` выключает tools, если явный `--tools` не переопределил privacy default. Промежуточные данные tools не записываются в историю, но провайдер получает результаты и может повторить их в финальном ответе. Значения, похожие на credentials, редактируются перед probe/disclosure; это не полное обнаружение секретов. После suspicious или incomplete результата автоматические последующие tool-вызовы блокируются.

Ограниченный локальный адаптер не является полным content-secret scanner. Он консервативно отклоняет sensitive path components, symlink, special/hard-linked files, traversal и неоднозначные имена. Точные allowlisted argv, лимиты файлов/путей и таймауты приведены в [Конфигурации](CONFIGURATION.md). Kernel/filesystem вызов может продолжаться после in-process deadline.

## Public web fetch

`security.web_fetch_enabled` — отдельная opt-in capability, по умолчанию выключенная. Она разрешает только ограниченный HTTP(S) GET без userinfo, нестандартных портов, cookies, ambient credentials, upload и произвольных методов. Проверяются literal IP и, при локальном resolve, все адреса назначения; для прямого соединения проверенный адрес фиксируется на момент dial. Redirect ограничен тремя переходами и сохраняет исходный origin. Ответ ограничен 256 КиБ и 15 секундами; URL — 2048 байт. Распространённые credential-подобные значения редактируются, а ограниченный ответ локально проверяется как недоверенный.

Когда destination разрешается HTTP(S)-прокси или SOCKS с remote DNS, этот прокси входит в trusted computing base: приложение не может самостоятельно проверить его DNS-ответ. Для `socks5://` имя разрешается локально и IP проверяется; `socks5h://` передаёт имя прокси. Выбранный proxy не обходится молча. Подробности маршрутизации — в [Конфигурации](CONFIGURATION.md).

## Файлы, credentials и дочерние процессы

Конфигурация должна быть обычным приватным файлом текущего пользователя. Symlink, hard link, special file и permission bits группы/остальных отклоняются до YAML parsing. В Windows native owner/ACL checks завершаются fail-closed, если descriptor нельзя проверить; cross-build не является Windows runtime-тестом. В Unix каталог данных создаётся с `0700`, файлы данных — с `0600`; эти права не шифруют сохранённые credentials и историю.

Окружение дочернего процесса по умолчанию фильтруется по явному allowlist: ключи провайдера и посторонние ambient variables не наследуются. Это defense in depth, а не секретная граница: host-команда всё ещё может читать доступные файлы и использовать host network. Управляемые процессы отменяются, а принадлежащая Unix process group/Windows job очищается; отделившиеся процессы и внешние broker остаются вне границы.

Диагностика провайдера не выводит raw request/response bodies, credentials и endpoint URL. Обычный вывод команд, prompts, включённая история, явно переданные context files и opt-in recovery payload не гарантированно очищены от секретов. `zev run` предупреждает перед отправкой captured failure output провайдеру; проверьте данные до opt-in. Pattern-based redaction неполна.

## Данные и приватность

История — локальные SQLite-данные, не зашифрованное хранилище. В ней могут быть запросы, уточнения, ответы провайдера и варианты команд; ротации по количеству нет. `--no-history` не открывает history для конкретного запроса, но не удаляет старые записи и не отключает диалог в памяти, отправляемый провайдеру. Logical deletion не гарантирует стирание из WAL/free pages, exports, backups или remote copies.

Файлы project context ограничены по размеру, confined текущим рабочим каталогом и проверяются на symlink и sensitive paths до сети. `--allow-sensitive-context` — явный opt-in для выбранного sensitive path; symlink всё равно запрещён. Текст, явно включённый в prompt, может уйти провайдеру.

Semantic embeddings истории по умолчанию выключены. При включении подходят только initial/refinement user messages; remote embedding раскрывает этот текст, а semantic/hybrid — и поисковый запрос. Vector rebuild требует явный `--yes` и показывает provider, model и eligible count.

## Проверка и известные ограничения

Тесты покрывают priority policy, binding/replay rejection grants, bounded shell/argv analysis, path checks tools, destinations/redirects web fetch, redaction/probe и CLI approval flows. Они не доказывают обнаружение всех shell-конструкций или секретов, не превращают application policy в OS isolation и не подтверждают native Windows runtime. Отсутствие предупреждения не означает безопасность. Доступные test targets описаны в [Разработке](DEVELOPMENT.md), текущие ограничения платформ — в [Профиле проекта](../../PROJECT.md).
