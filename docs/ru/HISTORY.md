# История

Zev сохраняет запросы, уточнения, ответы модели и варианты команд локально в
`~/.zev/history.db`. Автоматической ротации по количеству нет. История и embeddings —
чувствительные данные, а не зашифрованное хранилище: не включайте секреты в запросы.

> История доступна через запись query и явные команды истории. Автоматическая
> legacy-миграция завершается до возврата repository; семантический поиск включается
> явно и использует отдельно настроенный embedding-клиент. Команды установленной
> версии проверяйте через `zev history --help`.

## Хранилище и жизненный цикл

Если история открылась успешно, CLI сохраняет диалог по мере работы:

1. первоначальный user-запрос до первого обращения к провайдеру;
2. каждое уточнение отдельным упорядоченным user-сообщением до следующего обращения;
3. каждый структурированный ответ и все варианты команд одной транзакцией;
4. выбранную команду и наблюдаемый результат доставки/выполнения;
5. завершение, отмену или ошибку без удаления ранее сохранённых сообщений.

Выбор, печать или вставка команды **не доказывают её выполнение**. Аварийное завершение
процесса может оставить диалог `started`, а результат выполнения неизвестным. Ошибки
записи истории дают предупреждение, но не повторяют уже выполненную команду.

Диалоги, сообщения, ответы и команды имеют отдельные полные ID. Создание/добавление
с тем же ID и неизменным содержимым идемпотентно; конфликтующее содержимое отклоняется.
Query recorder не сохраняет system prompt и автоматически собранное окружение.
Диагностика, явно включённая в user-сообщение, является его частью, в том числе при
проверке допустимости embedding.

SQLite использует внешние ключи, WAL, пятисекундный busy timeout и транзакции связанных
записей. База получает POSIX-режим `0600`, новые каталоги приложения — `0700`. В Windows
явный DACL разрешает полный доступ только текущему пользователю и SYSTEM, включая sidecar-файлы
БД и архивы миграции. Защищайте также WAL/SHM, экспорты и резервные копии. Это не изоляция
от враждебных процессов того же пользователя.

`HISTORY_ENABLED=false` и `--no-history` пропускают открытие истории: для этого запроса
не создаются БД, импорт или embeddings. Они не удаляют существующую историю и не убирают
текущий диалог из памяти, передаваемый провайдеру команд. Явные команды истории — отдельные
операции, на них этот opt-out для query не распространяется.

## Автоматический переход со старого JSONL

При открытии repository существующий `~/.zev/history` импортируется автоматически до
возврата активного хранилища. Этот путь используют и запросы с историей, и явные команды
истории. Если нет источника и незавершённого импорта, происходит обычная
инициализация/открытие SQLite.

Импорт удерживает lock старого файла, проверяет снимок открытого файла по идентичности,
размеру, времени изменения и SHA-256 и читает JSONL построчно. Он создаёт локальные
поисковые документы, не embeddings, и не обращается к сети. Каждая строка становится
диалогом; отсутствующие уточнения и результаты выполнения не выдумываются. После commit
и проверки количества источник переименовывается без перезаписи существующего архива:

```text
~/.zev/history.migrated.<sha256-prefix>.<UTC-timestamp>.<UUID>.jsonl
```

Журнал хранит путь будущего архива до rename; активация завершается после проверки
архива. Повтор может завершить проверенный импорт или восстановить активацию, прерванную
после rename. Fingerprint и идентичность строк предотвращают дублирование; две одинаковые
исходные строки остаются двумя записями. Неверные JSON/ответы и противоречивый выбор
прерывают импорт с номером строки и кодом ошибки, без содержимого. Изменение источника
отклоняется; восстановление может удалить только импортированные строки незавершённого
запуска и повторить импорт. Источник, отличающийся от уже завершённого импорта, вызывает
конфликт, а не автоматическое слияние.

Сохраняйте источник/архив для восстановления; не удаляйте его вручную для обхода ошибки.
Остановите старые JSONL-клиенты перед обновлением и не запускайте их после перехода:
dual-write отсутствует. Архив — не активное хранилище, `clear` его не удаляет.
Legacy-файл должен быть обычным приватным файлом (на Unix права не шире `0600`).

## Просмотр и управление

```bash
zev history
zev history show <conversation-id>
zev history show --message <message-id>
zev history export --format json
zev history export --format jsonl
zev history delete <conversation-id>
zev history clear --yes
```

`show` выводит JSON. Экспорт пишет полные представления диалогов в stdout; права файла
при перенаправлении определяет shell. Используйте приватный каталог и `umask 077`.
Удаление каскадно удаляет сообщения, ответы, команды, поисковые документы и embeddings;
`clear` требует `--yes`. Удаление логическое, не forensic erase WAL/свободных страниц,
экспортов, backup, legacy-архивов и удалённых копий. Активную WAL-базу копируют согласованным
SQLite-снимком/backup-механизмом, а не копированием только `history.db`.

## Сохранение последней команды как алиаса

```bash
zev alias last recent
zev recent
```

Локальная команда использует выбранную команду диалога, упорядоченную по времени выбора,
а не первый вариант модели. Подходят только завершённые диалоги с наблюдаемым результатом
`injected`, `printed` или успешным `executed`. Отменённые/неуспешные диалоги,
невыбранные варианты и неопределённая доставка пропускаются. Команда не выполняется,
не загружает настройки LLM/embedding и не делает сетевых запросов. Пустая история и
существующее имя алиаса дают ошибку; существующий алиас не перезаписывается. Запись идёт
через обычное YAML-хранилище `~/.zev/aliases`; фигурные скобки в команде экранируются.

## Продолжение предыдущего диалога

`zev continue` (или `zev query --continue`) восстанавливает последний завершённый
или ошибочный query вместе со всеми сообщениями. В интерактивном режиме по порядку
предлагаются файлы проекта, многострочный лог команды и уточнение; хотя бы один ввод
обязателен. Полная предшествующая переписка сохраняется в необязательном поле метаданных
`conversation_history`, а старые записи без него остаются читаемыми.

## Поиск

По умолчанию поиск локальный лексический, без embedding-провайдера:

```bash
zev history search "большие файлы" --limit 20 --json
zev history search "network error" --from 2026-01-01 --to 2027-01-01
zev history search "docker" --type command --provider ollama
zev history search --exact-command 'git status --short'
zev history search --literal -- '--dry-run'
```

- `--mode lexical|semantic|hybrid`: lexical объединяет surface-, stemmed- и typo-списки;
  semantic использует cosine similarity user-сообщений; hybrid объединяет lexical/vector
  через reciprocal rank fusion (RRF). Включите отдельный embedding-клиент ниже и явно
  постройте векторы сохранённых сообщений. Если embeddings отключены или векторизация
  поискового запроса не удалась, поиск явно переходит на lexical. Пустой векторный
  индекс возвращает пустой semantic-результат с показателями покрытия в JSON.
- `--fuzzy auto|always|off`: `auto` расширяет поиск, если исходных surface/morphology-
  кандидатов меньше запрошенного лимита; `always` включает расширение, `off` отключает.
- `--literal`: точная подстрока канонического текста с учётом регистра и пунктуации;
  обходит морфологию, опечатки и embeddings. Может сканировать сохранённый текст.
- `--exact-command`: сравнение полной команды байт-в-байт после проверки UTF-8;
  обходит расширение/embeddings и имеет приоритет над текстом поиска. Не выполняет команду.
- Фильтры: `--provider`, `--model`, `--status started|completed|cancelled|failed`,
  `--type user|assistant|command|explanation`, `--dangerous` / `--dangerous=false`,
  `--from` / `--to`. Даты задают полуоткрытый UTC-интервал `[from, to)`; дата без времени —
  полночь UTC. Признак опасности применяется к документам, связанным с командой.
- `--limit`: 1–1000 (по умолчанию 20). Пустой текст допустим только с `--exact-command`.
  Ввод экранируется/токенизируется, а не исполняется как raw FTS5 expression.

Лексический порядок ставит точное совпадение всех слов выше morphology и typo-only.
Surface/morphology-уровни используют RRF score, новое время и ID источника; typo-only
сначала упорядочиваются по проверенной близости всех слов, затем преобразуются в RRF
rank list. RRF использует `sum(1 / (60 + rank))`, rank начинается с 1, а не складывает
raw BM25 и cosine scores. Hybrid-сервис отдельно объединяет lexical/vector-списки;
его порядок не сохраняет lexical quality tiers. Каждое слово запроса должно совпасть
через выбранный lexical-путь; typo expansion не является any-term поиском.

Фильтры документов применяются до каждого FTS-лимита кандидатов. Каждый FTS-список
сохраняет не более 5000 документов; typo dictionary lookup ограничен 256 кандидатами
на путь lookup/expansion, hybrid fusion — 1000 результатами каждого lexical/vector-
списка. Literal и exact-command не используют эти FTS-лимиты. Semantic сканирует все
актуальные совместимые векторы, но хранит в памяти только страницу с lookahead.
Это фиксированные ограничения реализации, не пользовательские настройки.

`--json` содержит полные ID источников (`documentId`, `conversationId`, `messageId` и,
где применимо, `commandId`), диалог, тип документа, время, snippet,
`score`, `scoreKind`, `matchSources`, `requestedMode`, фактический `mode`, `degraded`,
`embeddingCoverage`, `truncated` и, при наличии, `nextCursor`. Передайте токен через
`--cursor`, повторив остальные параметры запроса, включая limit и фильтры:

```bash
zev history search "большие файлы" --limit 20 --json --cursor '<nextCursor>'
```

Курсор привязан к запросу, профилю и ревизии данных; изменения данных/индексов делают
его недействительным — начните поиск заново. `nextCursor` продолжает текущий ranked
set, не обходит лимиты кандидатов. `truncated` отражает обнаруженные границы кандидатов/
удерживаемого окна, а не обычный конец страницы. Ни `truncated=false`, ни отсутствие
курсора не гарантируют неограниченный typo recall или полное embedding-покрытие;
проверяйте также `embeddingCoverage` и `degraded`. Hit сохраняет UUID исходного сообщения
или команды, а не внутренний номер FTS-строки; команда и пояснение также различаются
типом документа. Поиск никогда не выполняет найденную команду.

### Морфология и опечатки

Профиль `snowball-v0.10.0-nfkc-casefold-yo2e-v1` применяет NFKC, Unicode case folding,
нормализацию пробелов и `ё`/`е`, затем русский/английский Snowball stemming по токенам.
Примеры: `файл`/`файла`/`файлы`/`файлов`, `file`/`files` и
`connect`/`connected`/`connecting`. Другие письменности сохраняют surface-токены.
Это ограниченный stemming, не полная лемматизация: `go`/`went`/`gone` и синонимы не обещаны.

Поиск опечаток использует локальные token/deletion-key индексы и Unicode edit distance
с перестановкой соседних символов. Query-токены короче четырёх символов не расширяются;
четыре–пять допускают одну правку; более длинные — не больше двух и 30% длины большего
токена. Расширение ограничено query-токенами до 32 символов, 600 deletion keys и
наборами до 256 кандидатов на lookup/expansion path. Смена профиля требует rebuild индексов,
а не смешивания старых и новых токенов.

## Семантическая конфигурация и обслуживание индексов

Семантика отключена по умолчанию и настраивается отдельно от LLM команд:

```dotenv
HISTORY_SEMANTIC_ENABLED=false
HISTORY_EMBEDDING_PROVIDER=openai-compatible
HISTORY_EMBEDDING_BASE_URL=https://embedding.example/v1
HISTORY_EMBEDDING_MODEL=text-embedding-model
HISTORY_EMBEDDING_DIMENSIONS=1536
HISTORY_EMBEDDING_API_KEY=replace-me
HISTORY_EMBEDDING_MAX_BYTES=32768
```

Укажите реальные модель и размерность, поддерживаемые endpoint. Клиент добавляет
`/embeddings`; ключи/заголовки провайдера команд не наследуются. Слишком длинный UTF-8 ввод
отклоняется, а не обрезается молча; сохранённое сообщение остаётся доступным лексически.
Допустимы только `user`-сообщения с kind `initial_prompt` или `refinement`, никогда
команды, assistant/system text или metadata. Совместимость векторов задают модель,
размерность, профиль и content hash. Удалённый запрос раскрывает user-текст;
semantic/hybrid также раскрывает поисковый запрос. `localhost` может быть forwarding proxy;
для удалённых endpoint используйте HTTPS. Для активации CLI-клиента задайте
`HISTORY_SEMANTIC_ENABLED=true` с корректными настройками endpoint; `false` в примере
выше показывает значение по умолчанию.

Обычный query не создаёт embeddings, не индексирует старые сообщения и не подставляет
найденное в новый LLM prompt (нет автоматического RAG). Обслуживание индексов явное:

```text
zev history index status --json
zev history index rebuild --fts
zev history index rebuild --vectors --yes
zev history index rebuild --vectors --retry-failed --yes
```

`status` показывает готовность lexical и числа eligible/ready/failed/stale embeddings
для выбранного профиля. Выберите ровно один флаг: `--fts` (локальный rebuild без
embedding-запросов) или `--vectors`. Vector rebuild выводит провайдера, модель и общее
число допустимых сообщений в stderr, затем требует явный `--yes`, в том числе при
неинтерактивном запуске. Это размер допустимой совокупности, а не точное число передач:
актуальные ready-векторы пропускаются; failed повторяются только с `--retry-failed`,
который требует `--vectors`. Pending/stale обрабатываются ограниченными страницами.
Ошибки embeddings сохраняют канонические сообщения и фиксируют контролируемый статус
failed. При недоступности вектора поискового запроса поиск отмечает lexical fallback
через `degraded` и предупреждение; в JSON предупреждение включено в результат, а не
печатается отдельным текстом. Полный cosine scan стоит O(N × dimensions), использует
потоковое чтение векторов и отмену; это не ANN и не гарантия постоянной задержки.
