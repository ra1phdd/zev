# Обновление Zev

```bash
zev update [stable|main]
```

По умолчанию используется канал `stable`: Zev проверяет последний **стабильный
GitHub Release** в `ra1phdd/zev`, скачивает архив для своей ОС и архитектуры,
проверяет SHA-256 по `checksums.txt` из того же релиза и заменяет запущенный
исполняемый файл. Команда `zev update main` скачивает исходники текущего коммита
`main` и собирает их локально установленным Go toolchain перед заменой. Ни один
канал не запускает установочный shell-скрипт и не использует ключи LLM, адреса
провайдеров или дополнительные HTTP-заголовки провайдера. Сборки stable с
известной версией автоматически не понижаются.

Для обычных интерактивных/query-команд Zev синхронно выполняет startup-проверку
обновлений в режиме best effort с таймаутом 5 секунд. Она пропускается для справки,
`version`, machine-output (`--print`/`--json`) и команд списков provider/alias/script.
Ошибки и таймауты не мешают запуску команды. Неудачная проверка кешируется на 1 час,
успешная — на 24 часа в `~/.zev/update-check.json`. Проверка не создаёт `~/.zev` или
lock-файл кеша, если каталог отсутствует. Кешированный или успешный результат может
вывести уведомление; выполните `zev update` для установки стабильного релиза или
`zev update main` для сборки последнего коммита разработки. Флаг `--proxy URL`
применяется и к этой проверке.

Явная операция `zev update [stable|main]` имеет таймаут 1 минута для сетевой
загрузки и установки. Скрытая операция `zev update --migrate-only` сохраняет
отдельный таймаут 10 минут для локальных миграций.

Ветка `main` активно разрабатывается и может содержать ошибки и регрессии.
Совместимость между `main` и стабильным релизом не гарантируется; при возврате к
`stable` может потребоваться вручную исправить файлы или переустановить Zev.

До замены проверенный кандидат должен подтвердить поддержку протокола
самообновления Zev. Релизы, выпущенные до этой возможности, отклоняются: вместо
миграций нельзя случайно запустить обычный запрос. Старый Zev без `update` сначала
нужно обновить способом из [README](../../README.ru.md).

## Граница миграции данных

После установки **новый исполняемый файл** сразу запускает оркестрацию локальных
миграций до открытия соответствующего хранилища:

- конфигурация: поддерживаемый dotenv-файл v1.0.0 `~/.zev/config` преобразуется в
  текущий версионированный YAML напрямую;
- алиасы и скрипты: неверсированные метаданные v1.0.0 преобразуются в текущие metadata v2;
- история: SQLite инициализируется одной встроенной SQL-миграцией (`.up.sql`),
  затем отдельно импортируется JSONL из v1.0.0.

Текущие readers в `internal/core` и `internal/entities` принимают только актуальные
форматы. Они не распознают legacy-данные, не интерпретируют dev-схемы и не запускают
миграции при чтении или записи. Нужная миграция должна быть завершена оркестрацией до
использования хранилища. JSONL-importer не является шагом SQLite-схемы, а SQL-база не
воспроизводит историю dev-схем.

Если будущий выпущенный формат меняет хранилище, его переход между релизами сохраняется
и включается в цепочку для пользователей, пропустивших релизы. Development-снимки не
являются обратно совместимыми входами миграции. Поддерживаемый источник или переход
нельзя выводить из не выпущенной схемы.

Ни одна миграция не создаёт архив, sidecar-архив или резервную копию. Существующие
резервные копии, экспорты и другие исторические копии пользователя находятся вне
протокола миграции: Zev не обещает обходить или удалять их, а миграция не является
безопасным стиранием.

Миграции не генерируют AI-метаданные, не обращаются к LLM, не перестраивают embeddings,
не выполняют сохранённые скрипты и не меняют настройки провайдера. Явные миграции
обновления запускаются и при отключённой истории запросов. Отсутствующий каталог
`~/.zev` не создаётся. Независимые шаги запускаются даже при ошибке другого шага;
отмена останавливает дальнейшую работу. Каждый мигратор поддерживает собственное
восстановление; общей атомарной транзакции над всеми хранилищами нет.

Восстановление ограничено journal или importer ledger текущего протокола, если состояние
источника и назначения совпадает. Zev не разбирает и не восстанавливает архивы/journal
без маркера или незавершённые артефакты dev-снимков и не обходит неизвестные пути.
Изменённая, повреждённая или конфликтующая запись блокирует операцию без догадок.
Общие файловые примитивы `internal/migrations/filetxn` обеспечивают staging, публикацию,
классификацию сохранности и recovery только для файловых миграций. Это не механизм
транзакций/отката SQLite и не rollback для CRUD скриптов.

Даже если установленная версия актуальна или новее релиза, Zev запускает миграции.
Поэтому повторный `zev update` позволяет завершить миграцию после предыдущего сбоя.
Для повтора без сети установленным исполняемым файлом:

```bash
zev update --migrate-only
```

Этот служебный флаг намеренно скрыт из обычного списка справки.

## Ошибки и границы установки

Перед обновлением сделайте резервную копию `~/.zev`. Ошибки скачивания, checksum,
архива, совместимости и подготовки установки оставляют прежний бинарник на месте.
Обновление сериализует сотрудничающие команды update и подготавливает замену рядом
с установленным файлом, а не обрезает работающий файл. Символическая ссылка запуска
разрешается до настоящего установленного файла.

Автоматическая замена исполняемого файла поддерживается на Linux и macOS.
В Windows `zev update` отказывается от замены: установите проверенный релиз вручную
и затем выполните `zev update --migrate-only`.

Процессу нужны права записи в каталог исполняемого файла. Zev не вызывает `sudo`
и не запрашивает повышение привилегий автоматически. Для защищённой установки или
установки через пакетный менеджер используйте соответствующий механизм обновления.
Алиас или скрипт с именем `update` не переопределяет встроенную команду; переименуйте
его, если раньше запускали собственную сущность через `zev update`.

Если замена завершилась, а миграция — нет, команда завершается с ошибкой и
**оставляет новый исполняемый файл**. Автоматического отката бинарника нет:
часть хранилищ уже могла обновиться, и старая версия может перестать их читать.
Исправьте указанную локальную проблему и повторите миграцию. Аварийное завершение
между заменой и миграцией тоже требует повтора; синхронная проверка при запуске
ограничена пятью секундами, кеширует сбои на час и не заменяет исполняемый файл
и не запускает миграции.

Checksums из того же GitHub Release проверяют целостность, но не являются независимой
подписью издателя. Ошибки GitHub/сети и API rate limits возвращаются как ошибки,
а не как успешное «обновление не требуется». Проверка выполнения на каждой целевой
ОС остаётся отдельной от кросс-компиляции.
