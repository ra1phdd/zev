# Спецификация: постоянная история, FTS и векторный поиск

**Статус:** draft

## 1. Цель и границы

Новая история Zev должна сохранять полный жизненный цикл диалога локально, без ограничения на последние N записей, поддерживать точный полнотекстовый поиск и дополнительный семантический поиск по смыслу пользовательских запросов.

В область этой спецификации входят:

- SQLite как постоянное хранилище истории;
- сохранение всех сообщений текущего диалога, включая каждое уточнение пользователя;
- стабильные идентификаторы диалогов, сообщений, ответов и предложенных команд;
- FTS-поиск по словам, тексту сообщений, объяснениям и shell-командам, включая русскую морфологию и устойчивость к опечаткам;
- векторный индекс **только для пользовательских сообщений и уточнений**;
- импорт существующего JSONL-файла;
- CLI для поиска, просмотра, экспорта и удаления записей;
- приватность, транзакционность, миграции и восстановление после неполного запроса.

Векторный индекс не должен создаваться для команд, объяснений ассистента, system prompt, метаданных провайдера или другого текста, который не был пользовательским сообщением. Векторный поиск не является автоматическим RAG: найденные записи не добавляются в новый запрос к модели без отдельного явно определённого режима.

## 2. Нормативные термины

Ключевые слова **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT** и **MAY** имеют обычный смысл требований RFC 2119.

- **Диалог** (`conversation`) — одна история запроса с первоначальным сообщением, уточнениями, ответами модели и результатом выбора/выполнения.
- **Сообщение** (`message`) — упорядоченный элемент диалога с ролью `user`, `assistant` или `system`.
- **Уточнение** — отдельное пользовательское сообщение после первоначального запроса. Оно не перезаписывает первоначальный запрос.
- **Ответ** (`response`) — структурированный `OptionsResponse`, полученный от провайдера.
- **Команда** (`command`) — один вариант shell-команды из ответа модели.
- **Лексический поиск** — поиск по словам и токенам через SQLite FTS5.
- **Семантический поиск** — поиск по embedding пользовательских сообщений и уточнений.

## 3. Требования к данным

### 3.1. Идентификаторы

Все сущности MUST иметь собственный идентификатор:

- `conversation_id` — идентификатор диалога;
- `message_id` — идентификатор сообщения;
- `response_id` — идентификатор ответа модели;
- `command_id` — идентификатор предложенной команды.

Идентификаторы SHOULD быть UUIDv4, сгенерированными через криптографически безопасный источник случайности. Они хранятся как TEXT в каноническом lowercase-представлении. Короткие значения, показанные в TUI, являются только отображением полного ID и не могут использоваться как первичный ключ.

Идентификатор должен быть создан до первой записи диалога. Повторная попытка записи после сбоя не должна создавать новую сущность, если используется тот же ID.

### 3.2. Диалоги

Таблица `conversations` MUST содержать как минимум:

| Поле | Тип | Требование |
|---|---|---|
| `id` | `TEXT PRIMARY KEY` | UUID диалога |
| `created_at` | `TEXT` | RFC3339 UTC |
| `updated_at` | `TEXT` | RFC3339 UTC |
| `status` | `TEXT` | `started`, `completed`, `cancelled`, `failed` |
| `kind` | `TEXT` | тип запуска, например `query` |
| `provider` | `TEXT` | имя провайдера, nullable до первого ответа |
| `model` | `TEXT` | модель, nullable до первого ответа |
| `selected_command_id` | `TEXT` | nullable |
| `metadata_json` | `TEXT` | необязательные расширяемые метаданные |

История MUST хранить диалоги без ограничения количества. Удаление старых записей по достижении фиксированного лимита запрещено. Политика retention, если она появится, должна быть отдельной явной настройкой и не может быть скрытой ротацией.

### 3.3. Сообщения

Таблица `messages` MUST содержать:

| Поле | Тип | Требование |
|---|---|---|
| `id` | `TEXT PRIMARY KEY` | UUID сообщения |
| `conversation_id` | `TEXT NOT NULL` | FK на `conversations` с `ON DELETE CASCADE` |
| `sequence` | `INTEGER NOT NULL` | монотонный порядок внутри диалога |
| `role` | `TEXT NOT NULL` | `user`, `assistant`, `system` |
| `kind` | `TEXT NOT NULL` | `initial_prompt`, `refinement`, `response`, `system_prompt`, `error` |
| `content` | `TEXT NOT NULL` | полный текст сообщения |
| `created_at` | `TEXT NOT NULL` | RFC3339 UTC |
| `metadata_json` | `TEXT` | необязательные метаданные |

Уникальное ограничение `(conversation_id, sequence)` MUST исключать повторные номера. Номер выделяется атомарно в транзакции записи; время не заменяет порядок. Записанные сообщения неизменяемы. Повтор с тем же ID и тем же payload возвращает существующую сущность, с другим payload — конфликт без перезаписи.

Каждое уточнение пользователя MUST записываться отдельной строкой с `role = 'user'` и `kind = 'refinement'`. Нельзя заменять им `initial_prompt` или хранить только последний текст в поле диалога.

`content` пользовательского сообщения должен быть точным текстом, который был сформирован для этого сообщения и передан модели. Если пользовательский ввод был дополнен диагностическим выводом, этот вывод хранится внутри того же `content`; отдельная таблица для логов в рамках этой истории не создаётся. Поле `metadata_json` не является заменой содержимому сообщения и не индексируется семантически.

Модель сообщения MUST допускать дополнительные типизированные части (`parts_json` с версией формата) как расширение для будущих видов входных данных. Текст пользовательского сообщения остаётся в `content`; дополнительные части не являются отдельными сообщениями, не индексируются FTS автоматически и не попадают в embeddings без отдельного решения.

System prompt и автоматически собранное окружение по умолчанию не сохраняются. В текущем коде нет отдельной настройки сохранения system prompt; эта спецификация её не вводит. Тип `system` зарезервирован для расширения и тестов исключения из индексов.

### 3.4. Ответы и команды

Таблица `responses` MUST хранить полный структурированный ответ модели:

- `id TEXT PRIMARY KEY`;
- `conversation_id TEXT NOT NULL`;
- `message_id TEXT NOT NULL` — сообщение ассистента;
- `provider TEXT NOT NULL`;
- `model TEXT NOT NULL`;
- `payload_json TEXT NOT NULL`;
- `is_valid INTEGER NOT NULL`;
- `created_at TEXT NOT NULL`.

Таблица `commands` MUST хранить варианты отдельно от JSON-ответа:

- `id TEXT PRIMARY KEY`;
- `response_id TEXT NOT NULL`;
- `conversation_id TEXT NOT NULL`;
- `ordinal INTEGER NOT NULL`;
- `command TEXT NOT NULL`;
- `short_explanation TEXT`;
- `is_dangerous INTEGER NOT NULL`;
- `dangerous_explanation TEXT`;
- `selected_at TEXT`;
- `executed_at TEXT`;
- `execution_exit_code INTEGER`;
- `execution_error TEXT`.

Уникальное ограничение `(response_id, ordinal)` MUST сохранять порядок вариантов. Команды не являются векторными документами. Их можно индексировать для FTS и искать точным/структурным поиском.

## 4. SQLite-хранилище

### 4.1. Файл и режим работы

Основной файл MUST быть `~/.zev/history.db`. При первом открытии history-модуля существующий `~/.zev/history` MUST автоматически мигрировать в SQLite. Исходный файл не перезаписывается: после успешной проверки он автоматически переименовывается в архивный файл рядом с базой. После миграции путь `~/.zev/history` больше не является активным хранилищем.

SQLite MUST использовать:

- `PRAGMA foreign_keys = ON`;
- WAL для обычной работы;
- ограниченный `busy_timeout`;
- транзакции для связанных записей;
- атомарные миграции через таблицу `schema_migrations`;
- права файла не шире `0600` при создании.

Репозиторий MUST не читать всю базу и не переписывать её при каждой новой записи. Добавление сообщения, ответа или команды должно быть append/update-операцией внутри короткой транзакции.

Выбор SQLite-драйвера должен сохранять заявленную возможность CGO-free кросс-компиляции Zev. Если конкретный драйвер или расширение SQLite нарушает это требование, он не принимается без отдельного решения и проверки всех целевых платформ.

### 4.2. Транзакции и частичные диалоги

Запись должна происходить по мере выполнения запроса:

1. создать диалог и сохранить первоначальное user-сообщение;
2. после каждого уточнения добавить отдельное user-сообщение;
3. после каждого ответа добавить assistant-сообщение, response и commands;
4. при выборе обновить выбранную команду;
5. после выполнения записать результат и итоговый статус диалога;
6. при отмене или ошибке сохранить доступные сообщения и выставить `cancelled` или `failed`.

Сбой после сохранения user-сообщения не должен приводить к потере запроса. Сбой после сохранения ответа не должен удалять предыдущие сообщения. Повтор операции с тем же ID должна быть идемпотентной или возвращать контролируемую ошибку конфликта.

### 4.3. Автоматический мигратор JSONL → SQLite

Мигратор запускается автоматически при первом открытии history-модуля, если существует `~/.zev/history` и активная база `~/.zev/history.db` ещё не содержит завершённой миграции этого источника. Пользователь не должен вручную запускать отдельную миграционную команду для обычного перехода на новую версию. Мигратор выполняется до чтения или записи обычной истории и блокирует параллельный запуск второго мигратора.

Миграция должна следовать этому алгоритму:

1. Проверить пути, права и отсутствие недопустимого конфликта. `~/.zev/history` должен быть обычным файлом, а `history.db` — SQLite-базой ожидаемой версии либо отсутствовать.
2. Создать базу и схему в `~/.zev/history.db`, если они ещё не созданы. Схема и FTS5 создаются обычными версиями SQLite-миграций.
3. Получить стабильный fingerprint исходного файла до чтения: размер, `mtime` и SHA-256 содержимого. Файл читать через открытый дескриптор; после чтения повторно проверить, что файл не изменился.
4. Создать запись в `migration_runs`/import ledger со статусом `running`, fingerprint источника и версией формата.
5. Прочитать JSONL построчно, не загружая весь файл в память. Каждая строка импортируется как отдельный диалог с `metadata_json.source = "legacy_jsonl"`, `source_line` и fingerprint строки. Поля `prompt`, `response`, `provider`, `model`, `selected_command` и `selected_index` преобразуются в `conversations`, `messages`, `responses` и `commands`.
6. Старый формат не содержит уточнений, поэтому мигратор не должен их выдумывать. Импортированный `prompt` становится одним `initial_prompt`; дополнительные уточнения отсутствуют.
7. Для каждой импортированной записи в той же транзакции создаются FTS-документы. Embeddings старых записей во время миграции не создаются автоматически; их построение выполняется только отдельной операцией индексации и только для импортированных user-сообщений.
8. Обработать валидные и повреждённые строки по согласованному режиму: по умолчанию любая ошибка формата прерывает миграцию до активации результата, а отчёт содержит номер строки, код ошибки и количество обработанных строк без вывода payload. Частичный импорт не должен считаться завершённым.
9. Зафиксировать импорт одной транзакцией или возобновляемыми транзакциями с ledger. В ledger сохранить число строк, число импортированных диалогов, число пропущенных/ошибочных строк и fingerprint. Статус остаётся `running` до итоговой проверки, затем становится `verified`; `completed` допустим только после архивирования. Записи незавершённого run не видны обычным операциям history; до завершения миграции они заблокированы, чтение/запись JSONL не используется как fallback.
10. Повторно проверить fingerprint исходного файла. Если файл изменился во время миграции, миграция считается неуспешной, её результат не активируется, а пользователь получает ошибку с предложением повторить запуск.
11. После успешной фиксации и проверки количества записей атомарно переименовать исходный файл в архивный путь вида `~/.zev/history.migrated.<fingerprint-prefix>.<timestamp>.jsonl`. Архив создаётся с правами не шире `0600`; существующий файл с тем же именем не перезаписывается.
12. Только после успешного переименования считать SQLite-историю активной и записать в ledger `archived_path` и статус `completed`. Если переименование не удалось, база остаётся доступной для повторной проверки, но активный legacy-файл сохраняется; повторный запуск не должен дублировать импорт благодаря fingerprint и line identity.

Путь архива MUST записываться в ledger до переименования, чтобы восстановиться при crash между переименованием и финальной фиксацией статуса. При повторном запуске `verified`/незавершённый run возобновляется: если исходник отсутствует, а записанный архив имеет ожидаемый SHA-256, мигратор завершает активацию без повторного импорта. Несовпадение архивного хеша или отсутствие обоих файлов — ошибка, а не основание создать пустую историю. Изменившийся источник незавершённого run требует отмены только принадлежащих этому run импортированных строк и повторного импорта проверенного снимка; пользовательские записи в уже существующей базе не удаляются.

Миграционный lock MUST охватывать импорт и архивирование, а также использовать механизм блокировки legacy-хранилища для совместимых старых процессов. Старая версия не должна продолжать работать с JSONL во время/после перехода; запуск устаревших клиентов после миграции не поддерживается и не является dual-write режимом. Мигратор ничего не отправляет LLM или embedding-провайдеру. Query с `--no-history`/`HISTORY_ENABLED=false` не открывает хранилище и не запускает мигратор.

Мигратор не должен молча удалять, обнулять или перезаписывать `~/.zev/history`. Архивирование после подтверждённой миграции является обязательной частью автоматической замены старого хранилища; пользователь не должен вручную удалять старый JSONL. Обычные команды истории после миграции используют только `history.db`, а архив доступен для ручного восстановления и аудита.

Если `history.db` уже существует, но миграция этого fingerprint имеет статус `completed`, повторный запуск ничего не импортирует. Если база содержит завершённую миграцию другого fingerprint, изменение старого файла не импортируется автоматически в активную базу: мигратор сохраняет новый файл как отдельный конфликт и сообщает о нём, чтобы не создавать дубликаты или незаметно смешивать две истории.

## 5. FTS5

### 5.1. Объём индекса

SQLite FTS5 MUST индексировать следующие типы документов:

- `user_message` — первоначальные запросы и уточнения;
- `assistant_message` — текстовые представления ответов модели, если они сохранены;
- `command` — shell-команды;
- `explanation` — объяснения команд и опасности.

Минимальные поля документа:

- `document_id` — ID сообщения, ответа или команды;
- `conversation_id`;
- `document_type`;
- `content`;
- `command`;
- `explanation`;
- `created_at` как `UNINDEXED` значение для выдачи и фильтров.

System prompt и необязательные метаданные MUST NOT попадать в FTS без отдельной настройки приватности. Индекс должен обновляться в той же транзакции, что и исходная запись, либо иметь проверяемый механизм восстановления.

### 5.2. Русская и английская морфология, устойчивость к опечаткам

Поиск по обычному тексту MUST иметь как минимум три лексических представления документа:

1. `surface` — исходные токены для точного поиска;
2. `normalized` — Unicode NFKC, case folding, нормализация `ё/е` по выбранному профилю и очистка повторяющихся разделителей;
3. `morphology` — языковые леммы или стемы, полученные версионируемым analyzer-портом.

В `morphology` MUST попадать формы одного слова. Для русского acceptance-набор включает `файл`, `файла`, `файлы`, `файлов`; для английского — как минимум `file`, `files`, `connect`, `connected`, `connecting`. Для английского analyzer MUST учитывать английскую морфологию, а не сводиться к Unicode normalization и surface token. Для неизвестных языков используется language-neutral fallback: Unicode normalization плюс surface token; он не должен выдумывать русские или английские леммы.

SQLite FTS5 не предоставляет готовый русский или английский lemmatizer. Поэтому реализация должна выбрать и закрепить language-aware analyzer после небольшого benchmark/spike, а не притворяться, что `unicode61` решает морфологию. Предпочтителен lemmatizer, поддерживающий русские и английские формы, включая нерегулярные формы; stemmer допустим как fallback только для явно ограниченного acceptance-набора. Analyzer должен иметь `profile_id` и версию, быть детерминированным и использоваться одинаково для индекса документа и запроса. Смена analyzer делает `morphology`-индекс stale и требует rebuild; старые и новые токены нельзя молча смешивать.

Морфологический индекс применяется к пользовательским сообщениям и уточнениям, assistant text и explanations. Язык выбирается по language profile и/или по скрипту токена: кириллица анализируется русским профилем, латиница — английским профилем по умолчанию; смешанный текст обрабатывается по токенам. Командные токены не должны случайно переключать язык всего сообщения. Для `command` каноническим остаётся исходный shell-текст: морфологическое преобразование не должно менять, нормализовать или подменять полную команду. Exact command search всегда сравнивает исходное значение.

Опечатки MUST обрабатываться отдельным fuzzy-слоем, а не только embeddings:

1. построить дополнительный FTS5 trigram-индекс для текстовых поисковых полей;
2. получить ограниченный набор кандидатов по пересечению/совпадению триграмм;
3. для токенов-кандидатов посчитать Unicode-aware Damerau–Levenshtein или эквивалентную edit distance в Go;
4. принять совпадение только при пороге, зависящем от длины токена: слова короче 4 символов требуют exact match, 4–5 символов допускают не более 1 edit, от 6 символов — не более 2 edits и не более 30% длины;
5. ранжировать fuzzy-hit по `typo_similarity`, а не выдавать его как обычный BM25.

Расстояние считается по Unicode code points после нормализации, не по UTF-8 байтам. Транспозиция соседних символов считается одной ошибкой. Лимит 30% вычисляется от максимальной длины сравниваемых токенов. Trigram `MATCH` сам по себе не является fuzzy-search: полная ошибочная строка не передаётся ему как единственный шаблон; запрос строится из экранированных отдельных триграмм с OR. Нельзя требовать совпадения всех триграмм.

Одних триграмм недостаточно: `файл` и `фалй` не имеют общих триграмм, хотя различаются одной транспозицией. Поэтому MUST существовать дополнительный локальный словарь surface-токенов с индексом deletion keys (до двух удалений) или другой индексированный алгоритм поиска токенов в заданном edit distance. Этот путь обязателен для коротких слов и кандидатов без общих триграмм; полный scan всех сообщений запрещён. Кандидаты проверяются реальной edit distance, поэтому deletion-key collision не означает совпадения. При лимите кандидатов ответ отмечает `truncated`, а не обещает полное покрытие. Лимиты expansion/token length/candidate count фиксируются в analyzer profile и проверяются benchmark.

Для сочетания словоформы и опечатки pipeline исправляет токен в кандидаты surface-словаря, затем применяет к ним тот же русский analyzer и ищет по morphology-индексу. Это query expansion, а не изменение сохранённого пользовательского сообщения. Нормализация `ё → е` включена по умолчанию только для производных текстовых индексов. Стемминг (например, Snowball Russian или Snowball English) является минимальным вариантом морфологического поиска, но не полной лемматизацией: супплетивные формы и синонимы он не гарантирует; для нерегулярных форм вроде `go`/`went`/`gone` нужен lemmatizer, а не один stemmer. Точные поддерживаемые группы русского и английского фиксируются acceptance fixtures. Морфология и typo-поиск работают локально, без LLM, remote API, embeddings или обязательной native-зависимости. Точное совпадение по всем словам имеет приоритет перед результатом, основанным только на typo-expansion; RRF объединяет списки внутри документированного уровня качества.

Fuzzy-слой может искать команды для целей истории, но никогда не выбирает и не выполняет найденную команду автоматически. `--exact-command` отключает morphology/fuzzy expansion и сравнивает байт-в-байт (после проверки валидного UTF-8) сохранённый shell-текст.

Hybrid lexical ranking MUST объединять отдельные списки через RRF, а не складывать несопоставимые BM25, typo и vector scores. Результат сообщает `match_sources` (`exact`, `morphology`, `typo`, `semantic`) и `score_kind`. Если analyzer или trigram-индекс не построен, режим явно помечается `degraded`; silent fallback запрещён.

### 5.3. Индексы и лексический pipeline

Минимальная реализация должна иметь отдельные FTS5 virtual tables или эквивалентные versioned индексные представления:

- `history_fts_surface` — исходные/normalized tokens, tokenizer `unicode61`;
- `history_fts_morphology` — analyzer-токены lemma/stem, tokenizer без дополнительной морфологической логики;
- `history_fts_trigram` — `tokenize = 'trigram'` для bounded candidate retrieval при опечатках.

Все три индекса используют одинаковые `document_id`, `conversation_id`, `document_type` и version/profile metadata. Индексы могут быть contentless/external-content, но rebuild из canonical tables MUST быть возможен. Изменение canonical текста, analyzer profile или tokenizer profile делает соответствующие индексные строки stale и требует атомарного обновления либо последующего проверяемого rebuild.

Режим `--mode lexical` означает hybrid внутри лексического поиска: exact/surface, morphology и typo-кандидаты объединяются через RRF. По умолчанию fuzzy-поиск работает в режиме `auto`: он добавляется, если exact/morphology-кандидатов недостаточно для запрошенного limit; `--fuzzy always` разрешает его явно, а `--fuzzy off` оставляет только exact/morphology. Semantic vector search не является частью lexical mode.

Лексический поиск должен возвращать не только итоговый score, но и `match_sources`, чтобы пользователь видел, что совпадение найдено по словоформе или через исправление опечатки. Порядок tie-breaker остаётся детерминированным: score, затем `created_at DESC`, затем полный ID.

### 5.4. Поведение поиска

Команда поиска должна поддерживать как минимум:

```text
zev history search <text>
zev history search <text> --limit 20
zev history search <text> --from 2026-01-01 --to 2026-12-31
zev history search <text> --provider ollama
zev history search <text> --type user
zev history show <conversation-id>
zev history show --message <message-id>
```

Поиск MUST:

- возвращать диалоги и конкретные совпавшие документы;
- показывать `conversation_id`, дату, роль/тип, короткий snippet и score;
- иметь детерминированную сортировку: сначала релевантность, затем `created_at DESC`, затем ID;
- поддерживать limit и pagination/cursor;
- корректно обрабатывать пустой запрос и специальные символы FTS5;
- не выполнять raw FTS expression из пользовательского ввода без экранирования или явного режима расширенного синтаксиса.

Для shell-команд должны поддерживаться:

- поиск слов и токенов через FTS5;
- поиск полного совпадения по `commands.command`;
- фильтрация по провайдеру, модели, дате, статусу и признаку опасности.

FTS-поиск должен работать без настроенного embedding-провайдера.

## 6. Векторный индекс

### 6.1. Объём векторизации

Векторизуются **только** строки `messages`, удовлетворяющие одновременно условиям:

```text
role = 'user'
kind IN ('initial_prompt', 'refinement')
```

Запрещено создавать embeddings для:

- shell-команд;
- объяснений и предупреждений ассистента;
- assistant messages;
- system prompt;
- provider/model metadata;
- диагностических полей, не являющихся частью пользовательского сообщения.

Если пользовательский лог был включён в `content` user-сообщения, он является частью этого сообщения и может попасть в его embedding. Отдельный embedding для лога создавать нельзя.

### 6.2. Хранение embedding

Таблица `message_embeddings` MUST содержать:

- `message_id TEXT PRIMARY KEY`;
- `model TEXT NOT NULL`;
- `dimensions INTEGER NOT NULL`;
- `vector BLOB` — float32 в зафиксированном little-endian формате;
- `content_hash TEXT NOT NULL`;
- `created_at TEXT NOT NULL`;
- `status TEXT NOT NULL` — `ready`, `failed`, `stale`;
- `error TEXT`.

`content_hash` нужен для определения изменения текста и повторной генерации embedding. Нельзя считать embedding актуальным только по ID сообщения.

Для `ready` поле `vector` обязательно; для `failed`/`stale` оно может быть NULL. Новая запись ещё без embedding представлена отсутствием строки. Вектор должен содержать ровно `dimensions * 4` байт; NaN, infinity и нулевая норма недопустимы.

Каждая запись дополнительно хранит `profile_id`: идентификатор профиля, фиксирующего provider, model/version, dimensions, preprocessing version, cosine metric и кодировку. Запрос сравнивается только с `ready`-векторами своего профиля. `content_hash` — SHA-256 точного UTF-8 `content`; идентичные тексты разных сообщений не объединяются в одну сущность.

Базовая реализация должна хранить embedding в SQLite и выполнять cosine similarity в Go. Она не должна требовать SQLite-расширение с native-бинарником, если это ломает CGO-free сборки. При больших объёмах можно добавить отдельный ANN-адаптер, не меняя контракт истории.

### 6.3. Генерация и отказоустойчивость

Сохранение сообщения не должно зависеть от успешной генерации embedding. Embedding создаётся после фиксации сообщения или в отдельном явно контролируемом шаге.

Если embedding-провайдер отсутствует, недоступен или вернул ошибку:

- сообщение и FTS-запись всё равно сохраняются;
- поиск переключается на FTS;
- ошибка embedding фиксируется в `message_embeddings` или журнале диагностики;
- пользователь получает понятное предупреждение только там, где запрошен semantic/hybrid режим.

Embedding-модель и размерность являются частью конфигурации индекса. При смене модели старые vectors нельзя сравнивать с новыми: создаётся новая версия индекса либо записи получают статус `stale` и перестраиваются.

Удаление сообщения или диалога MUST удалять соответствующий embedding через FK/транзакцию. Восстановление индекса должно уметь найти все user-сообщения без актуального embedding.

### 6.4. Semantic и hybrid search

Semantic search возвращает совпавшие пользовательские сообщения и родительские диалоги. Он не должен подменять найденную пользовательскую формулировку командой из другой записи.

Рекомендуемый hybrid режим:

1. получить кандидатов FTS;
2. получить кандидатов по cosine similarity только из user/refinement embeddings;
3. объединить и дедуплицировать по `message_id`/`conversation_id`;
4. применить нормализованный reciprocal-rank fusion или другую документированную формулу;
5. вернуть объяснимые источники совпадения: `fts`, `semantic` или `hybrid`.

Команда поиска должна явно выбирать режим, например `--mode lexical|semantic|hybrid`. По умолчанию используется `lexical`, чтобы поиск был быстрым, предсказуемым и доступным без embedding-провайдера.

Векторные совпадения могут использоваться для просмотра истории, но автоматическая передача найденных диалогов в новый запрос к LLM в этой спецификации отсутствует.

## 7. Публичный интерфейс модуля истории

Конкретная реализация может отличаться, но внешний интерфейс должен скрывать SQL, FTS-парсинг, сериализацию и векторное вычисление. Минимальный набор операций:

```go
type Store interface {
    StartConversation(ctx context.Context, input StartConversationInput) (Conversation, error)
    AppendMessage(ctx context.Context, input AppendMessageInput) (Message, error)
    RecordResponse(ctx context.Context, input RecordResponseInput) (Response, error)
    RecordSelection(ctx context.Context, input RecordSelectionInput) error
    CompleteConversation(ctx context.Context, input CompleteConversationInput) error
    GetConversation(ctx context.Context, id string) (ConversationView, error)
    Search(ctx context.Context, request SearchRequest) (SearchResult, error)
    DeleteConversation(ctx context.Context, id string) error
}
```

Сервис должен принимать storage adapter через composition root. CLI не должен напрямую открывать SQLite или собирать SQL-запросы. Интерфейс поиска должен возвращать структурированный результат, пригодный как для TUI, так и для `--json`.

## 8. CLI-контракт

Существующая команда `zev history` сохраняет интерактивный просмотр, но теперь работает с SQLite и показывает диалоги, а не только финальные записи.

Минимальные команды:

```text
zev history
zev history search <query>
zev history show <conversation-id>
zev history export [--format json|jsonl]
zev history delete <conversation-id>
zev history clear
```

`clear` MUST требовать явного подтверждения или отдельного non-interactive флага. Удаление должно быть ограничено указанными ID, если пользователь не подтвердил очистку всей базы.

Для скриптов нужен `--json`. JSON-вывод должен включать полные ID, timestamp, тип документа, score, snippet и conversation ID. TUI может показывать сокращённые ID, но при копировании/действии должен использовать полный ID.

Флаг `--no-history` сохраняет текущую семантику: диалог, сообщения, FTS-документы и embeddings для этого запуска не сохраняются. Уже существующие записи не удаляются.

## 9. Приватность и безопасность

- Файл базы, временные файлы экспорта и резервные копии создаются с правами не шире `0600`.
- Тексты запросов, уточнений, команд и ответы модели считаются чувствительными данными.
- Секреты не должны попадать в логи приложения.
- Remote embedding provider не является обязательным и должен быть явно настроен; передача пользовательских сообщений наружу должна быть видимой в документации и настройках.
- Embeddings тоже считаются чувствительными данными: они не должны сохраняться в общий кэш или отправляться провайдеру без разрешения.
- Ошибки поиска и миграции не должны печатать полный payload, если это не запрос пользователя на экспорт.
- Удаление диалога должно удалять его сообщения, ответы, команды, FTS-документы и embeddings.

## 10. Совместимость и миграции

Схема должна иметь версию и последовательные миграции. Нельзя изменять структуру SQLite вручную без миграции.

Первая миграция должна:

1. создать `history.db` и базовую схему;
2. включить FTS5;
3. автоматически мигрировать старый JSONL при первом открытии history-модуля;
4. проверить fingerprint, количество строк, импортированных диалогов и ошибок;
5. сохранить статус миграции и ledger;
6. после успешной проверки переименовать исходный JSONL в архивный файл, не перезаписывая его.

Миграции должны быть идемпотентными и безопасно завершаться при прерывании процесса. Перед destructive-операциями нужен backup или явное подтверждение пользователя.

## 11. Тестирование и критерии готовности

### Unit-тесты

- создание диалога и уникальность ID;
- сохранение нескольких уточнений без потери первоначального запроса;
- сохранение partial/failed/cancelled диалога;
- идемпотентная запись с тем же ID;
- FTS-поиск по русским и английским словам;
- совпадение русских словоформ (`файл`/`файла`/`файлы`/`файлов`) и английских форм (`file`/`files`, `connect`/`connected`/`connecting`);
- выбранный lemmatizer обрабатывает проверенные нерегулярные формы (`go`/`went`/`gone`) либо явно сообщает, что они не входят в профиль stemmer;
- опечатки в кириллице и латинице с Unicode Damerau–Levenshtein;
- отсутствие ложных fuzzy-совпадений для коротких токенов;
- поиск флагов и shell-команд;
- экранирование специальных FTS5 символов;
- фильтры и детерминированная пагинация;
- cosine similarity и нормализация векторов;
- отсутствие embedding для assistant/system/command документов;
- повторная генерация при изменении `content_hash`;
- fallback с semantic/hybrid на FTS при недоступном embedding-провайдере;
- импорт валидных и повреждённых JSONL-строк;
- удаление всех зависимых записей.

### Интеграционные тесты

- конкурентная запись из двух процессов;
- восстановление FTS после прерванной транзакции;
- автоматическая миграция реального старого JSONL без интерактивного подтверждения;
- архивирование только после проверки, отказ при повреждённых строках и изменении источника;
- два одновременных мигратора, существующая база с пользовательскими записями, одинаковые строки и повторный запуск без дублей;
- crash до commit, после commit, до/после rename и до финальной активации;
- отказ переименования, занятый путь архива, неверный архивный хеш и восстановление ledger;
- отсутствие миграции при `--no-history`/`HISTORY_ENABLED=false` и отсутствие сетевых вызовов при импорте;
- чтение базы после перезапуска CLI;
- сохранение прав `0600`;
- работа на целевых платформах без обязательного CGO.

### Acceptance criteria

Функция считается готовой, если:

- после более чем 100 диалогов старые записи доступны;
- первоначальный запрос и каждое уточнение видны в правильном порядке;
- каждый диалог, сообщение, ответ и команда имеют собственный стабильный ID;
- поиск по словам, объяснениям и shell-командам работает без embedding-провайдера;
- lexical mode без сети и embeddings находит `файлов` по запросу `файл`, `резервные копии` по запросу `резервная копия`, а `ёлка` и `елка` совпадают в normalized-поиске;
- `--fuzzy always` находит `файл` по `фалй`, `docker` по `dokcer`, `резервная` по `резерная`; проверяются вставка, удаление, замена и транспозиция, сочетание опечатки со словоформой, а также непохожие слова за пределами порога;
- точные совпадения не вытесняются только typo-кандидатами; `--fuzzy off`, `--literal` и `--exact-command` не исправляют ввод; все производные индексы восстанавливаются после миграции/rebuild и каскадно очищаются при удалении;
- semantic search векторизует только user initial/refinement messages;
- в базе нет embeddings для команд и assistant messages;
- незавершённый или упавший запрос не теряет уже записанные сообщения;
- старый `~/.zev/history` автоматически мигрируется в `~/.zev/history.db`, после проверки исходный файл автоматически архивируется переименованием без перезаписи;
- `zev history`, `search`, `show`, `export` и удаление работают через единый history module;
- `make test`, `make test-race`, `make lint` и `make check` проходят после реализации.

## 12. Что не входит в эту спецификацию

- автоматическое добавление найденной истории в prompt модели;
- изменение формата ответа провайдеров;
- изменение правил выполнения или подтверждения shell-команд;
- хранение необработанного вывода команд как отдельной сущности;
- серверная БД или обязательный внешний search-сервис;
- автоматическая очистка истории по количеству записей.

## 13. Уточнения контрактов и проверка спецификации

### Целостность и жизненный цикл

Все ссылки между таблицами MUST иметь FK с каскадным удалением, кроме `selected_command_id`, для которого используется `ON DELETE SET NULL`. Сервис дополнительно проверяет, что выбранная команда принадлежит тому же диалогу; это обеспечивается составными ключами/ограничениями либо транзакционной проверкой. Boolean-поля ограничены `0/1`, `sequence` и `ordinal` — неотрицательными значениями, JSON — валидным документом.

`completed` означает завершение взаимодействия Zev, но не доказанное выполнение команды. Результат доставки отдельно различает `selected`, `injected`, `printed`, `executed`, `failed` и `unknown`. Вставленная в терминал команда не получает `executed_at` или exit code. После аварийного завершения `started` не превращается автоматически в `failed`: без доказанного завершения владельца другой процесс не может закрыть активный диалог. Неопределённое исполнение показывается как `unknown`, не как успех.

Ответ ассистента сохраняется полностью, а не только через `OptionsResponse.CompactJSON()`. Запись response, assistant message и всех command alternatives атомарна. Нельзя создавать по embedding строки команд из полного ответа.

### Лексические режимы и ранжирование

Базовый FTS tokenizer — `unicode61` с Unicode case folding и диакритической нормализацией. Он остаётся точным лексическим слоем, но НЕ является единственным поисковым механизмом: русская морфология и опечатки MUST поддерживаться отдельными индексами и этапами ранжирования ниже. Метаданные ID/type/date задаются `UNINDEXED`, структурные фильтры применяются через обычные таблицы. BM25 сортируется по возрастанию (меньшее значение лучше); JSON содержит `score_kind`, поэтому raw BM25 не выдаётся за cosine similarity.

Добавляются явные опции:

```text
zev history search --mode lexical --exact-command 'git status --short'
zev history search --mode lexical --literal -- '--dry-run'
zev history search 'большие файлы' --mode hybrid --json --limit 20
zev history search 'network error' --model MODEL --status failed --dangerous
```

`--exact-command` сравнивает полную команду без нормализации, `--literal` ищет точную подстроку с сохранением пунктуации и отключает morphology/typo/semantic expansion. Для literal-поиска `%`, `_` и escape-символ MUST экранироваться как данные; допустим parameterized substring scan с явно указанной стоимостью. `--` отделяет текст, начинающийся с дефиса. FTS не должен заявляться точным поиском shell-флагов: `--dry-run` и `dry run` могут давать одинаковые токены. Пустой positional query разрешён только при `--exact-command`; иначе это ошибка валидации.

Канонические типы фильтра `--type`: `user`, `assistant`, `command`, `explanation`; сервис сопоставляет их типам индексных документов. Date range — полуоткрытый UTC-интервал `[from, to)`; дата без времени означает UTC midnight. Фильтры применяются до top-K и пагинации во всех режимах. Совпадения не теряются при группировке: результат содержит conversation и массив matching documents с message/command IDs. Один и тот же текст из JSON-ответа и выделенной команды не должен искусственно удваивать ранк.

Hybrid использует RRF `sum(1 / (60 + rank))`, rank начинается с 1, а не сложение несопоставимых BM25/cosine scores. Команды могут входить в lexical-часть hybrid, но никогда не в vector-часть. Выдача указывает фактический режим, покрытие embedding и признак `degraded`; fallback semantic → lexical не может быть тихим. Страницы фиксируют query/filter/profile и watermark исходного набора; при изменении данных/индекса cursor отклоняется с понятной ошибкой, а не обещает snapshot consistency.

### Настройка и обслуживание vectors

`HISTORY_SEMANTIC_ENABLED=false` по умолчанию. Включение и выбор embedding-провайдера/модели — явный opt-in, отдельный от LLM для команд. Localhost не гарантирует приватности, если endpoint перенаправляет данные наружу. Индексирование старой истории не запускается автоматически при обычном запросе.

Целевые команды обслуживания:

```text
zev history index status --json
zev history index rebuild --fts
zev history index rebuild --vectors
zev history index rebuild --vectors --retry-failed
```

Rebuild vectors явно показывает provider/model и число пользовательских сообщений до подтверждения передачи; non-interactive запуск требует явного согласия. Нельзя обрезать слишком длинное сообщение молча: при лимите embedding-модели фиксируется контролируемая ошибка и сообщение остаётся доступным через FTS. Запись embedding повторно проверяет существование сообщения, hash и профиль внутри транзакции; конкурентное удаление или смена профиля не должны воскресить данные. Внешний HTTP-запрос не выполняется под SQLite write lock.

Полный cosine scan имеет сложность O(N × dimensions), поэтому не обещается постоянная задержка при неограниченной истории. Реализация MUST иметь benchmark на фиксированных данных, отмену через `ctx`, bounded memory и не загружать все blobs в память. ANN добавляется только по измерениям и отдельному решению.

### Приватность, миграция и ошибки

`HISTORY_ENABLED=false` и `--no-history` запрещают также фоновые embeddings, создание новых файлов и импорт в ходе отключённого query. Явные команды чтения существующей истории не удаляют её. `CONTEXT_ENABLED` управляет отправкой окружения, но не является разрешением хранить system prompt или вложения.

Права `0600` применяются на POSIX; на Windows требуется эквивалентное ограничение ACL. Каталог должен быть закрыт от других пользователей, WAL/SHM sidecars и временные файлы — защищены так же, как база. Логическое DELETE не гарантирует forensic erase из WAL, свободных страниц, backup или старого JSONL. Удаление из истории не должно ложно обещать удаление всех внешних копий.

Миграция JSONL автоматическая при первом открытии history-модуля; пустая база без исходного файла означает обычную первую инициализацию. Import ledger фиксирует fingerprint источника и line identity так, чтобы повтор не дублировал данные, но две одинаковые исходные строки сохранялись как две записи. Один и тот же источник импортируется по проверенному снимку, изменение файла во время импорта отклоняется. Повреждённые строки по умолчанию прерывают миграцию до активации результата; они показываются в отчёте, не удаляются и не включают payload в ошибку. Неизвестная более новая версия схемы открывается с понятной ошибкой, без downgrade. Backup активной WAL-базы создаётся через SQLite backup API или согласованный snapshot, а не копированием только `.db`.

Типизированные ошибки модуля: `not_found`, `invalid_query`, `conflict`, `busy`, `cancelled`, `storage_failure`, `unsupported_schema`, `embedding_unavailable`. `errors.Is`/`errors.As` должны сохранять классификацию. Сбой записи истории даёт явное предупреждение, не маскируется успехом сохранения и не повторяет уже выполненную shell-команду. TUI выводит сохранённый текст как данные с экранированием control/ANSI sequences.

### Архитектура, проверки и открытые решения

SQL и миграции располагаются в `internal/entities/history/repository`, правила истории — в `internal/entities/history/service`, сетевой embedding-адаптер — в `internal/entities/history/client`; `cmd/zev` остаётся composition root и CLI. Минимальный consumer-side порт хранения и отдельный embedding-порт не должны заставлять repository отвечать за TUI или сетевой вызов. Go-стиль, `ctx` первым параметром, именованные input-типы, английские комментарии и тесты рядом с исходниками соответствуют правилам проекта.

Примеры выше — **проектируемые**, а не уже существующие CLI-команды. Для реализации применяются существующие проверки:

```bash
make test
make test-race
make lint
make check
make build
make clean
```

Дополнительные acceptance tests MUST доказывать: shell-флаги различаются в literal-режиме, fallback помечен degraded, отказ embedding не теряет запись, разные profile/model не смешиваются, crash не помечает неизвестное исполнение успехом, повторный импорт и запись идемпотентны, `--no-history` не создаёт side effects хранилища. Для английского отдельно проверяются plural, third-person singular, past tense, progressive и irregular verb forms; typo tests покрывают латиницу так же, как кириллицу.

До реализации остаются открытыми конкретный CGO-free SQLite-драйвер, русский и английский morphology analyzer/library и его language profiles, embedding provider/model и численные benchmark-бюджеты на согласованной машине. Их версии фиксируются после spike и проверки целевых архитектур; выдуманных зависимостей в `go.mod` эта спецификация не добавляет. Поскольку Context7 недоступен в текущем клиенте и SQLite ещё не закреплён в `go.mod`, технические требования сверены с [официальной FTS5 документацией](https://www.sqlite.org/fts5.html) и [PRAGMA reference](https://www.sqlite.org/pragma.html), [Snowball Russian stemming algorithm](https://snowballstem.org/algorithms/russian/stemmer.html) и [Snowball English stemming algorithm](https://snowballstem.org/algorithms/english/stemmer.html); поведение конкретного драйвера и выбранного analyzer предстоит подтвердить при реализации.

Спецификация не разрешает реализацию, изменение runtime-конфигурации, принятие ADR, установку зависимостей, миграцию пользовательской базы или коммит чужих изменений. После согласования документа можно перейти к отдельному плану реализации.
